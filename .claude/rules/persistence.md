# Persistence rules (`appStorage`, desktop data file, export/import)

The one-adapter rule (`appStorage`, never capture a storage at import time): root `CLAUDE.md` "State Management".

- `appStorage` (`lib/dataStorage.ts`, installed in `plugins/pinia.ts`; stores do not name a storage): `localStorage` on web, on desktop a synchronous mirror of `kan-do-data.json` that Rust owns (debounced atomic writes, flush on exit, ADR 008). Persisted keys live in `PERSISTED_KEYS` (`tasks-store`, `board-store`, `integration-health-store`, `taskStatistics`, `notionConfig`, `remindersConfig`, `propertyOptions`, `settings-store`, `day-recap-store`, `trash-store`, `topic-styles`; a Vitest guard fails when a store is missing); `kando-locale` and `statistics-backfill-state` stay in `localStorage`. The writer strips `SECRET_STATE_PATHS` itself (ADR 007).
- **`taskStatistics` extra fields (#537):** `dayEndInFlight` (`Record<YYYY-MM-DD, number>`, written by `useDayEndTracking`) and `discardedTime` (`{ taskId, deletedAt: epoch ms, seconds }[]`, written when a not-done task's delete reaches the trash, removed on restore) are additive: stored state without them hydrates to `{}` / `[]`, readers skip malformed entries, a wrongly shaped field (`null`, string, array for the map) falls back to the default in `afterHydrate`, both prune at 120 days. `workSessions` (#600, `{ start, end }` epoch ms, written by `composables/useWorkSessionTracking`: open on a timer arm, `end` by a 60 s heartbeat, never per tick; 120-day prune) follows it too. A new field of a persisted store follows the same rule (default in the setup store, tolerant reader, a hydrate test like `tests/store/taskStatisticsLegacy.test.ts`).
- **`remindersConfig` (#551):** the list roles (`lists`, `Record<listId, { role: 'topic' | 'off'; title }>`; the role `activity` of versions before #575 reads as `topic`, covered by `tests/store/remindersConfig.test.ts`) and the done-occurrence ledger (`doneOccurrences`, pruned at local midnight by the fetch), additive: nothing stored reads as no lists (a list not answered reads as `topic`), a malformed role reads as `topic` and a malformed ledger entry is dropped in memory (`afterHydrate`, no write); no secret, the permission is runtime state. `integration-health-store` gains `sources.reminders`: a state without it hydrates with the entry and is not written back (`healthNeedsWriteBack`). Tests: `tests/store/remindersConfig.test.ts`, `tests/store/hydrationNoWrite.test.ts`
- **Create doubts that outlive their task (#538, #535):** `trash-store` entries gain optional `createUncertain` and `pendingMove` gains optional `fromCreateUncertain` (same shape as `pendingSync.createUncertain`); older data has none, a malformed value reads as none (`normalizeCreateUncertain` in `lib/taskSources.ts`, no write), and `normalizePendingMove` keeps `fromSourceNotPlanned` through the read. `pendingMove.fromUpstreamDone` (#781, boolean, the origin's done state for the way back) is additive the same way: none or malformed reads as "not completed". Tests: `tests/store/trash.test.ts`, `tests/lib/taskSources.test.ts`
- **`board-store.focus` (#161):** `{ topic, day }`, the board's topic focus, additive: older data hydrates to `null`, a malformed value is dropped in memory by `afterHydrate` (`sanitizeFocus`, no write), and `activeFocusTopic` ignores a focus of an earlier local day, so it ends with its day without a write. Tests: `tests/store/boardFocus.test.ts`
- **`board-store.notPlannedOrder` (#354):** `string[]`, the ids of the tasks put back to "Alle Aufgaben" by hand, newest first; additive: older data hydrates to `[]`, a malformed value reads as `[]` in memory (`sanitizeNotPlannedOrder`, no write). Tests: `tests/store/boardNotPlannedOrder.test.ts`
- **The marker on a waiting task (#793):** `Task.notPlanned` now counts on a Wartet task too. `tasks-store.markerModel` (number, `MARKER_MODEL` = 2 in `lib/taskPlanning.ts`) stamps data written under that rule; `beforeHydrate` clears it, so stored data without it (or with anything else) reads as older: `afterHydrate` drops the field from Jetzt, Wartet and Erledigt tasks and from `pendingDeletes` snapshots once (`dropStaleMarkers`), sets the stamp in memory and writes only when a task changed. An export carries the stamp; a seed that holds a waiting task off today must write it (`buildTasksStore` does). Not cleaned: `trash-store` snapshots. Tests: `tests/store/tasks.hydrate.test.ts`, `tests/store/tasks.notPlanned.test.ts`
- **Connections and "not planned" (#357):** `Task.sourceNotPlanned` (string) and `PendingMove.fromSourceNotPlanned` are additive (a task without them merges as before); `notionConfig.notPlannedLimited` (boolean) and `statusMapping.notPlanned` (`string[]`, anything else stored reads as none) are additive too. Tests: `tests/store/tasks.sourceNotPlanned.test.ts`
- **New day (#356, #387):** the `day-recap-store` fields (`lastNewDay`, `sentBack`, `noticeClosedDay`, `timeOffer`, `planNoteSeen`), `tasks-store.afterMidnight` and the no longer read `firstBackDay`, `backNoteClosed` and `board-store.notPlannedFromWaiting`: `.claude/rules/new-day.md` (loads with the New day files; read it before touching one of these fields from another file). All additive, nothing writes at hydration.
- `afterHydrate` (pinia-plugin-persistedstate) runs even when nothing is stored: never `$persist()` there unconditionally, it writes `data_set` and an offline desktop launch counts as edited (#273)
- Desktop data safety (ADR 011): the guard lives in Rust's single write path (`src-tauri/src/data_file.rs`, `data_file/backup.rs`, `data_file/guard.rs`): a SHA-256 check before every write turns a foreign change into the blocking `conflict` status, an unreachable or slow (10 s) folder is `folder-unavailable` (nothing written, edits held in memory), backups are verbatim copies in `<folder>/backups/` (`daily` per local day, mandatory `pre-*` kinds block their operation). Never write the data path while `last_seen` is `None` or the status blocks; both versions go to `backups/` on every conflict choice. Export/import strip `SECRET_STATE_PATHS` in `utils/dataFile/exportImport.ts`. Web has the same export/import on `localStorage` (`composables/useWebDataTransfer.ts`, `utils/dataFile/webReplace.ts`, #238): replace-and-reload, this browser's tokens kept; `/settings/data` on web shows only that section.
- **App reset (kd#227, ADR 011 "App reset")**: `composables/useAppReset.ts` replaces the data with an empty envelope (desktop: `importApply`, so Rust's mandatory `pre-restore` backup comes first; web: `commitReset` removes every `PERSISTED_KEYS` blob, tokens included; never `planReplace`, it keeps tokens), calls `freezeWrites()` right after the replace (`appStorage.setItem` and `syncPendingChanges` do nothing), deletes every `SECRET_ENTRIES` Keychain entry and `reloadApp('/welcome')`. The erased set derives from `PERSISTED_KEYS` and `SECRET_ENTRIES`; `kando-locale`, `kando-last-seen-version` and the folder location are kept. A failed Keychain deletion keeps the question open; a retry skips the second replace, and closing it (Abbrechen, Esc, leaving the page) reloads the current page from the replaced file, because the frozen window must never outlive the reset.
- **Data status payload**: `emptyDataStatus(overrides?)` (`lib/dataStatus.ts`) is the single empty/ok `DataStatusPayload`; app state, `fakeDataBackend` and `tauriStub` start from it, so a new field is edited there and in `types/dataFile.ts` only.
- **Bundle identifier migration** (#42, ADR 019, `src-tauri/src/identifier_migration.rs`): runs in `setup` before `DataFile` exists; copies the legacy `com.julius.kan-do` folder (never writes it) and moves the four Keychain entries (production identifier, release builds only: a debug build with the production identifier never migrates and only reads the marker, legacy folder/service until the release has finished a step, the new ones after, kd#60; `npm run tauri:dev` runs under its own `….dev` identifier and never migrates, #413). The dev seed (`?seed=` in `plugins/e2e-seed.client.ts`) also writes into the data file through `seedDesktopStores` (`lib/dataStorage.ts`), but only while the file is empty, so a first `tauri:dev` launch shows the demo board and a later one keeps the dev data. A change to the identifier, the pointer or the backup layout keeps its tests (`cargo test --lib identifier_migration`) and never lets a failed copy become a first run.
- **Floating focus timer (#383, ADR 020):** `settings-store.floatingNowEnabled` (boolean) is additive: nothing stored reads as on, a non-boolean reads as on in memory (`afterHydrate`, no write). The window's position is machine-local and not in the data file: `overlay-window.json` in the app config dir, read tolerantly (`overlay::parse_position`, `resolve_position`). Every `data_*` command refuses a window other than `main` (`ensure_main_window`), so the pill window can never write. Tests: `tests/store/settingsFloatingNow.test.ts`, `cargo test --lib overlay`.
- **Automatic update check (#746):** `settings-store.autoUpdateCheck` (boolean, default on) follows the `floatingNowEnabled` rule: nothing stored or a non-boolean reads as on (`afterHydrate`, no write). Off: `plugins/updater.client.ts` skips the launch check. Tests: `tests/store/settingsAutoUpdateCheck.test.ts`, `tests/plugins/updater.test.ts`.
- **Intro hints (#800):** `settings-store.introHints` (`null`, or `{ on, quietDay, hints: Record<id, { answered, days }> }` with local day keys; rules in `lib/introHints.ts`) is additive: nothing stored reads as `null` (the hints never started: every install from before #800 shows none), a malformed value reads as `null` and a malformed hint entry or day key is dropped in memory (`sanitizeIntroHints` in `afterHydrate`, no write); an unknown hint id is kept. The ids are `start`, `weiter`, `auswahl`, `abschluss` (#801; `planen` follows with #803). Two entry points write a record: the welcome setup's endings (`startIntroHints`, `pages/welcome.vue`, keeps a record that is there) and "Erneut zeigen" in Einstellungen, Board (`restartIntroHints`, #804: replaces any record, also from `null`, which is how an install from before #800 gets hints); "Ausschalten" only sets `on` to false and keeps the record. A step already done when a record is replaced answers its hint at once (`useIntroHintSteps` watches the unanswered state). It travels in the `settings-store` blob, so export/import and the app reset carry it, and it is never sent to a connection. Tests: `tests/store/settingsIntroHints.test.ts`, `tests/lib/introHints.test.ts`, `tests/composables/useIntroHints.test.ts`, `tests/composables/useIntroHintsSwitch.test.ts`.
- **Welcome and Jetzt (#853):** the hints record gains `v` (2 on a record `freshIntroHints()` wrote; absent on an older one, which therefore never shows the welcome, id `welcome`) and `ownJetzt` (true once the user put a card into Jetzt themselves, written by `useTaskSync`; gates the hint "Weiter"); both additive, any other stored value reads as absent (`sanitizeIntroHints`, no write). `settings-store.jetztUsed` (boolean, a card was in Jetzt at least once: the dashed Jetzt placeholder never shows again) follows the `floatingNowEnabled` rule with default `false`. Tests: `tests/store/settingsIntroHints.test.ts`, `tests/lib/introHints.test.ts`, `tests/composables/useIntroHints.test.ts`.
- **Rust**: `npm run verify` has no cargo step; a change under `src-tauri/` runs `cargo test --lib` there (3-5 times when it adds a timing test; prefer gates such as `mpsc`/`Condvar` over short timeouts).
