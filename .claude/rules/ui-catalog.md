# `/ui` Components engine (#66, epic #58 D2/D3)

- **One entry per component**: `catalog/<category>/<Name>.catalog.ts`, `export default { ... } satisfies CatalogEntry` (`catalog/types.ts`). Plain data, a type-only import (Node 24 loads it for `scripts/ui-manifest.mjs`), no helper call. The folder is the manifest category, the file name the component name; `entryProblems` (`dev-tools/ui-catalog/validateEntry.ts`, run by `tests/devtools/ui-catalog/entries.test.ts`) enforces it, also unknown state labels, repeated ids and i18n keys missing in `de.json`/`en.json`.
- **Text lives once**: an app component's description, usage and avoid stay in its doc block (the entry has none); a Nuxt UI component (`source: 'nuxt-ui'`) has no doc block, so its entry carries them and the manifest row is built from it. Alternatives are component names with a manifest row.
- **Variants**: Nuxt UI components declare `matrix.axes` and `theme`; the values come from the merged theme (`#build/ui/<theme>.ts` + `app.config.ts`), never retyped. App components list named `variants`. `states` use the labels of `CATALOG_STATES` (loading, empty, error, disabled, focus, long-text, icon-only, selected, open); an overlay renders as its closed trigger (`trigger: true` with a slot text shows the default slot as a button), because an open overlay is portalled out of the sample and covers the page; `open: true` is for an overlay that renders inline. Sample copy is `{ $t: 'key' }`, so the language toggle switches it.
- **No samples**: a component that cannot render from plain props (needs a store, a trigger element or a host) sets `sampleNote: '<why>'` and lists no variants or states; the page prints the reason, `entryProblems` rejects an entry that has neither samples nor a reason.
- **Sample host** (#77): an app block that reads the stores renders through `host: 'board'` on its entry (`BoardSampleHost.vue`: a throwaway Pinia seeded with the demo board, its own stack-expansion state (`STACK_EXPANSION_STATE`: BoardColumn prunes stacks on mount) and a `DragDropProvider`, never the real stores, stacks or `appStorage`); an example's `demoTasks` passes one demo column as the `tasks` prop. A whole-page block (`Board`) or one that needs its list (`BoardColumnItem`) keeps a `sampleNote`. `tests/devtools/ui-catalog/boardSampleHost.test.ts` guards the isolation.
- **Tier** (derived, `tierOf` in `scripts/ui-manifest.mjs`): `kit` = every Nuxt UI component, everything under `components/ui/`, and an app component with three or more consumers; everything else is a `feature` part, grouped by its `area` (the folder under `components/`). Never tag it. **Every kit component needs an entry** (`missingEntries`, `tests/devtools/ui-catalog/entries.test.ts`); a feature part may have one when it renders from fixtures, and goes without otherwise. A new kit component brings its `catalog/<category>/<Name>.catalog.ts` in the same PR.
- **Generated data is derived or split, never one shared file** (#117): the manifest is built from the doc blocks and `catalog/` where it is read (`buildManifest()`; `nuxt.config.ts` hands it to `/ui` as `__UI_MANIFEST__`, a doc-block edit needs a `nuxt dev` restart), so there is nothing to regenerate or merge. The fingerprint is one file per component, so PRs that add or change different components never conflict.
- **Dev-only**: `catalog/` is imported only from `dev-tools/ui-catalog/` (a test greps for it); never from `components/`, `composables/` or app code. The build-output test (`tests/config/ui-catalog-build-output.test.ts`) lists the strings that must not reach a production build.
- **Style fingerprint**: `tests/e2e/ui-catalog.spec.ts` records the computed styles of every sample (of the component, not the host frame of a hosted one) (`tests/e2e/helpers/fingerprint.ts`) in `tests/e2e/snapshots/ui-catalog/<Component>.json`, one file per component (#117). A theme token, `app.config.ts` or component style change moves it on purpose: `PORT=<free> npm run test:e2e -- tests/e2e/ui-catalog.spec.ts --update-snapshots`, then commit the JSON files (a rename or removed component drops its file; record against the production build, as CI runs it, never `nuxt dev`). It is part of the gate's `design` specs. A merge conflict in these files means both sides changed the same component's styles: take either side and re-record.
