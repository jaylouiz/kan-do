# ADR 011: Backups, restore and cloud-sync conflict safety for the data file

## Status

Accepted (#224, part of epic #221). Builds on ADR 008 (file-backed persistence) and ADR 007 (secrets); the updater of ADR 009 calls its `pre-update` backup.

## Context

The data file lives in a folder the user chooses, often one that a sync client mirrors to a second Mac. Without a guard the app could overwrite a change made elsewhere, write an empty file over data that is merely unreachable, or lose the only copy during a migration or restore. The rule that decided every trade-off below: the data can never be silently lost or overwritten, and when a choice is needed the user sees exactly two versions and both are kept.

## Decision

- **The guard lives in Rust's single write path** (`Shared::write_locked`, gated by `Shared::inspect`). Direction A of the #224 options; per-task merge (B) and write-time-only checks (C) were rejected.
- **The hash decides, the header explains.** `last_seen` is `{ hash (SHA-256 of the bytes last read or written), writtenBy, writtenAt }`, set on load and after every own write, together with the file's size and mtime. Before every write the file is statted; only when size or mtime moved is it re-read and hashed. A different hash means someone else wrote it: status `conflict`, the write is refused, nothing is overwritten. Identical bytes rewritten by a sync client are not a conflict. A file whose size/mtime changes between two stats 500 ms apart is "still syncing" and re-checked later instead of declared a conflict. A vanished file keeps the `missing-file` rule (never recreated from memory), and a file this process never read (`last_seen` is `None`) is never replaced.
- **Status model.** `Status` gains `conflict` and `folder-unavailable`; both block writes. Priority when several apply: `read-only-*` > `conflict` > `folder-unavailable` > `write-failed` > `missing-file`. The payload also carries non-blocking `conflictCopies` (list) and `backupError`, plus `conflict { theirs, localChanges, mineTaskCount, autoReload }` while in conflict.
- **Watcher.** One std thread, no `notify` crate: every 15 s and on window focus it stats the file (hash only when size/mtime changed), detects a gone folder and scans the top level for conflict copies. It only reads and flags; the result is applied only when generation, status, folder and `last_seen` did not move during its I/O (so a probe that described this process's own older write is dropped). It keeps looking during a `conflict` too: the conflict follows the file (a half-downloaded file becomes readable, a third device writes) and clears itself when the file is the known version again. While the folder is unavailable it retries with backoff 5 s to 60 s; "Erneut versuchen" restarts it. A file that reappears after being missing, unreadable or unreachable is compared with `last_seen`: same hash recovers (pending edits are flushed), anything else is a `conflict`.
- **Bounded I/O.** Every read or write of the folder runs on a helper thread with a 10 s deadline (`guard::run_timed`); a timeout is `folder-unavailable`. A write carries an abandon flag checked right before its rename, so a call that finishes late can never land after the state machine gave up. An evicted iCloud file that is still downloading therefore never blocks the UI thread and never writes late. Commands that touch the folder run on the blocking pool.
- **Hard rule while `folder-unavailable`:** nothing is written to the data path: no empty file, no partial write, no temp file, no recreated folder (`init` after `missing-file` requires the folder to exist, `write_backup` creates only one directory level). Edits stay in memory; the notice says the board shown is not the saved version. Launching while unavailable hydrates empty without write-back. On recovery with no edits made meanwhile the window reloads by itself (at most once per 30 s, otherwise the modal asks); with edits it goes through the same two-version choice. The persistence plugin only writes on a store mutation (`$subscribe`), never defaults at hydration (the one exception is `board-store` writing back a stored legacy Linear blob after sanitising it, #273; the guard test is `tests/store/hydrationNoWrite.test.ts`), so after such a launch every `data_set` is an edit (the first call for a key included) and `local_changes` is simply `dirty`; an automatic reload happens only when no store wrote anything. A launch whose stores all mutate at start-up therefore ends in the modal rather than losing an edit.
- **Backups** are verbatim copies of the last valid on-disk state in `<folder>/backups/`, named `<UTC yyyymmddThhmmssZ>-<kind>-<device6>.json` (unique per device, so a synced `backups/` never conflicts with itself). Kinds: `daily`, `manual`, `pre-migration`, `pre-restore`, `pre-replace`, `pre-update`, `conflict`, `unsaved`. The state to copy is verified against `last_seen` first; a corrupt, blocked or changed file is never backed up as "mine". Retention is per kind and per device (newest 14 `daily`, newest 10 `manual` and `pre-restore`, never the newest of a kind), run after a successful backup. `conflict`, `unsaved`, `pre-migration`, `pre-replace` and `pre-update` are never rotated: each can be the only copy of the other device's file, of edits that never reached the file, or of the state before a migration, update or folder replace, and they only grow with rare, user-visible events. `daily` is the previous on-disk state before the first write of each local day (local day from an injectable clock: `libc::localtime_r` offset, no new crate beyond `libc`). Mandatory backups (`pre-migration`, `pre-restore`, `pre-replace`, `pre-update`) block their operation when they fail; a failing `daily` or `manual` backup never blocks saving and shows an orange line on the data page.
- **Restore and import** flush first, take a `pre-restore` backup, replace the file with the source bytes verbatim through `write_atomic`, bump the generation (the old webview's `data_set`s are dropped) and let the window reload; older schemas migrate on that load with their own `pre-migration` backup. A newer-schema or unparsable source is refused. Allowed from `ok`, `write-failed`, `missing-file` and `read-only-corrupt` (the recovery case: the unreadable file is first copied verbatim as `pre-restore`; not when the unreadable part is the location pointer). Refused in `conflict` (the two-version modal is the way), `read-only-newer-schema` (update the app instead) and `folder-unavailable`; the UI states the reason per status (`restoreBlockedBy`). The replace never runs over a file this process has not read: out of `missing-file` the path is probed again first (a file that reappeared is classified like any other change and the restore stops), and the commit step re-checks right before the rename that the target is still absent or still exactly the bytes just copied (`DataError::Changed` otherwise). Import takes the webview's already stripped JSON (`utils/dataFile/exportImport.ts`: the pure functions strip `SECRET_STATE_PATHS` both on export and on import, drop unknown store keys and reject non-kan-do and newer-schema files), so Rust never sees secrets and a hand-edited token never reaches the data file.
- **Conflict resolution.** "Diese Version behalten": the other file is read again at click time, and the decision is made on those bytes: refused when it has a newer schema, when I hold no edits, or when it is not the version the modal showed (`DataError::Changed`; the modal then shows the current one). Otherwise it is copied to `backups/` as `conflict` and mine is written, the commit re-checking that the file is still those bytes. "Andere Version laden" / "Neu laden": my in-memory state goes to `backups/` as `unsaved` first and only then does the window reload; a failed backup aborts. Quitting with an unresolved conflict writes `unsaved` instead of touching the main file. Quitting keeps edits in every state that could not write them (a missing or unreadable file, a failed or still settling write as well; not `read-only-newer-schema`, whose in-memory stores this build must not re-render). A reload (`load`) that cannot flush edits (blocked, failed, conflict) saves them as `unsaved` instead of dropping them.
- **Cloud conflict copies** (`kan-do-data*.json` other than the data file, top level only, parseable as an envelope: Dropbox "conflicted copy", iCloud `kan-do-data 2.json`, Syncthing `.sync-conflict-`) are listed, restorable (copy stays) and can be filed away into `backups/` as `conflict` (copy first, then remove). Nothing is ever deleted otherwise.
- **#222 carry-over fixed here:** a first-run write whose pointer cannot be saved keeps the file known and retries instead of getting stuck read-only (N5); `move`/`replace` no longer need the old folder to be writable (L1); "start here" never rebuilds a vanished folder tree (L7); a reload keeps edits it could not flush (L10); `render` borrows the stores instead of cloning them under the lock (L11).
- **Updater hook (#225).** `updater::pre_update_backup` calls `DataFile::backup(PreUpdate)` (pending edits are written first) between the flush and the install; any failure, and the new `conflict` / `folder-unavailable` data states, stop the install (`BackupFailed`, `DataBlocked`), so an update never runs without a fresh backup.
- **UI.** New sections on `/settings/data`, new `DataStorageNotice` states, one conflict modal and one restore/import modal (see DESIGN.md). The notice also appears on the welcome page, where an unavailable launch lands.

## Consequences

- Every failure mode is "write blocked plus notice", never a silent overwrite: a bug in the guard blocks saving, it does not lose data.
- Backups share the folder's fate: if the folder is unreachable so are its backups. A local-only second copy is out of scope.
- While the folder is unavailable at quit, edits that never reached the folder are lost (no local shadow; deliberately a single source of truth).
- A migration step still has to change a store value, and the backup before it is part of the migration: when it fails the app stays read-only on the untouched file.
- The five never-rotated backup kinds (`pre-migration`, `pre-replace`, `pre-update`, `conflict`, `unsaved`) grow without bound (#255 N4): each can be the only copy of something and they are rare, user-visible events, so growth is one verbatim data file per event. The files in `<folder>/backups/` can be removed by hand; `BackupKind::keep()` points here.
- A reload cannot be vetoed from Rust, and keeping the old in-memory copy across `load` would risk a stale write over a changed file. So a failed `unsaved` backup in `load` is surfaced as `backup_error` (not cleared by `load`) and those edits are lost (#255 L1, known limit; see the doc comment on `DataFile::load`).
- A conflict copy that vanishes between the scan and a restore or "Ablegen" (`NotFound`) leaves `conflictCopies` at once, with the status emitted; the error returned to the caller is unchanged (#255 N2). A restore out of `ok`/`write-failed` commits only over the bytes its `pre-restore` backup just copied (`Expect::Bytes`), so a change in between is `DataError::Changed` with the file untouched and the `pre-restore` kept (#255 N3).
- Verified by `cargo test` (name round trip, retention, daily once per local day across midnight, hash conflict vs identical bytes, both conflict resolutions, vanished file, unavailable folder, restore gates, conflict copies, unsaved on exit), Vitest and Playwright with the stubbed IPC. Real two-device cloud conflicts and iCloud eviction need the manual checklist in the PR.
- **Web export/import (#238)** uses the same file and the same pure functions, with `localStorage` instead of the data file: `composables/useWebDataTransfer.ts` downloads `buildExport` of the `PERSISTED_KEYS` blobs and, after `parseImport` and a confirm modal (default-checked safety download), replaces only those keys (`utils/dataFile/webReplace.ts`; a failed write rolls back) and reloads. This browser's own secrets at `SECRET_STATE_PATHS` are re-applied from the current blobs, never taken from the file. No backups, folder or conflict handling on web.

## Cloud upload state (#271)

With the folder in iCloud Drive the file stays readable and writable offline and iCloud uploads it later, so no `Status` ever fires, yet the backup purpose of a cloud folder and a second device depend on that upload. The app now says so quietly:

- **A non-blocking payload field, not a status.** `StatusPayload.cloudSync` (`{ state: uploading | pending | error | uploaded, message, since, visible }`) follows the `conflictCopies` / `backupError` pattern. It never changes `Status`, never gates or delays a write, is transient (never written to the data file) and is `None` for every status other than `ok` / `write-failed` and after a folder switch (`forget_folder_state`).
- **iCloud only.** The reader (`data_file/cloud.rs`, macOS) builds a fresh `NSURL` per read (resource values are cached per instance) and asks for `NSURLIsUbiquitousItemKey`, `...IsUploadedKey`, `...IsUploadingKey` and `...UploadingErrorKey`. Every other folder and every other provider answers `nil` for the attributes and shows nothing, which is today's behaviour; Dropbox, Google Drive, OneDrive and Synology expose no upload state to other apps (to be confirmed on real installs, see the PR checklist). Other targets compile a stub that answers `NotCloud`.
- **Polling, not `NSMetadataQuery`.** The read runs in the existing watcher tick (15 s, plus window focus) through `run_timed`, outside the lock, and is applied under the same "generation, status, folder and `last_seen` did not move" guard. `NSMetadataQuery` needs a run loop, has an unverified scope for a user-chosen folder and gains nothing at a 15 s cadence. A read that times out or fails leaves the previous value and is never a `folder-unavailable`; `emit` fires only when the payload changed.
- **Grace in Rust.** `uploading` / `pending` carry `visible: false` for `Timing::cloud_grace` (`CLOUD_GRACE_SECS`, 5 min) from the first not-uploaded look; only `uploaded` resets it, so continuous offline editing does not postpone the notice. An `error` follows the same grace (#289): an offline Mac may report it, and the data is safe locally either way; its reason `message` is still carried. The grace uses `Instant`, injectable through `Timing`. The data page ignores `visible` and shows the live state.
- **UI.** `DataStorageNotice` shows the notice last in its priority (after every other status and conflict copies); `useDataFolder().needsAttention` includes it, so the welcome and tasks pages behave alike. `/settings/data` gets one muted line for iCloud folders (DESIGN.md "System notice"). It is `neutral` and one copy for `uploading`, `pending` and `error` (#289); the error reason shows on `/settings/data` only. The cloud notice alone has an "Ausblenden" action: `useDataFolder` keeps one session-wide flag in memory, never persisted; `uploaded`, an escalation to `error` and a folder change do not clear it, only a reload or restart does, and `needsAttention` follows.
- **Tests.** `cargo test` with an injected fake reader covers the mapping, the grace, errors, folder switch, blocking statuses and a hanging read, and one test runs the real reader against a tempfile and expects `NotCloud` (the `nil` path and the FFI link); the iCloud-positive path needs a real iCloud folder and is a manual checklist.
