# ADR 013: Developer ID signing, notarization and the CI release

## Status

Accepted (#228 phases 2 and 3, part of epic #221). Phase 1 (CSP) is [ADR 012](012-desktop-csp.md).

## Context

[ADR 009](009-release-pipeline-and-updater.md) ships ad-hoc signed bundles from a local script. Two consequences hurt once the app is used beyond one Mac: a first install needs right-click → *Open*, and the macOS Keychain ties item access to the app's code identity, so every ad-hoc update (new identity) triggers a Keychain re-prompt per stored token ([ADR 007](007-secrets-keychain.md)). Actions minutes were out of budget when this was decided (the repository has been public, with free minutes, since 2026-11-06), but the release should be reproducible on a runner. The owner has no Apple Developer account yet, so none of this can be exercised for real; it must be safe to merge now and correct on first use.

## Decision

- **Ad-hoc stays the committed default; Developer ID is configuration.** `bundle.macOS.signingIdentity` remains `-`. Tauri's CLI lets the environment variable `APPLE_SIGNING_IDENTITY` override it, so a release becomes a Developer ID release by setting that variable, with no commit. `hardenedRuntime` is set explicitly and `entitlements` points at `src-tauri/entitlements.plist`, which is **empty on purpose**: WKWebView's JIT runs in Apple's WebContent process, Keychain access via the Security framework and network access need no entitlement outside the sandbox, and nothing third-party is loaded. `allow-jit` is not assumed. The first notarized build is the real test; a needed key is added then, with its reason.
- **The script is the only guard against a half-notarized release.** `tauri build` signs with Developer ID but, when notarization credentials are missing, only logs "skipping app notarization" and still produces a bundle Gatekeeper rejects. So `scripts/release/signing.mjs` (pure, unit-tested) classifies the state (`ad-hoc`, `developer-id`, `missing-credentials`, `invalid-identity`), the preflight refuses everything but the first two, and also refuses a Developer ID identity whose certificate is not in the Keychain (not checked when `APPLE_CERTIFICATE` imports it, as in CI). After a Developer ID build, the script runs `codesign --verify --deep --strict`, `spctl -a -vv` and `xcrun stapler validate` and aborts before anything is uploaded.
- **Credentials: environment first, Keychain second, never printed or written.** The identity, the `.p8` path, the Apple ID and the team id are environment-only (plain configuration). The Issuer ID, Key ID and app-specific password fall back to Keychain items (`kan-do-apple-api-issuer`, `kan-do-apple-api-key-id`, `kan-do-apple-app-password`), read only on a real local release. `--dry-run` asks whether an item *exists* (no `-w`, no prompt, no secret read) and prints the intended steps with placeholders. Values reach only the bundling child's environment, and the Keychain is read only when the identity is a Developer ID one (not for an ad-hoc release or `--bump-only`). The two notarization methods Tauri supports (API key, Apple ID) are both accepted; the API key is the documented one.
- **Each secret reaches one child, and the build is two children.** `tauri build` runs `nuxt generate`, npm lifecycle scripts and every crate's `build.rs`, so handing it the updater key, the `.p12` and a write token would expose them to any compromised dependency. The script therefore runs `tauri build --no-bundle` (frontend and compile) with a neutral environment, then `tauri bundle` (package, codesign, notarize, sign the updater bundle) with the updater key and the chosen Apple variables; `gh` gets the GitHub token; git, npm and the post-build checks get none (`signing.mjs` `SECRET_VARIABLES`, `neutralEnv`, `githubEnv`, `buildSigningEnv`). `tauri build --no-bundle` needs no key (the updater key is read only while bundling, `tauri-cli` `bundle.rs`); the split was smoke-tested on tauri-cli 2.12.4 with a throwaway key (no key for the first child, a signed `.app`, `.dmg`, `.app.tar.gz` and a `.sig` that records the version from the second). The script itself imports no npm package, so it is the only code that holds the secrets as a whole; the workflow still puts them in one step's `env`.
- **CI never silently falls back to ad-hoc.** The workflow passes `--require-developer-id`, which turns an ad-hoc result into a preflight refusal, so an empty or renamed `APPLE_*` secret fails the run. A manual dispatch with `allow_adhoc` opts out, and the run then prints a `::warning::`.
- **Build environment is sanitised.** Tauri notarizes whenever an identity (even `-`) and credentials are present, and Apple rejects an ad-hoc bundle, so an ad-hoc build is run without any `APPLE_*` variable; a Developer ID build gets only the variables of the chosen method (Tauri prefers the Apple ID triple, and a half-set one fails the build).
- **CI reuses the script, not `tauri-action`.** `tauri-action` would create its own `latest.json` with `browser_download_url`s, which cannot work for a private repository (ADR 009: API asset URLs plus a token), and would duplicate the signing and asset logic. `.github/workflows/release.yml` instead calls `scripts/release.mjs <version> --ci`, so the preflight, signing, verification, asset names and manifest are the same code. `--ci` starts from a pushed tag: it skips the local-release guards (on `main`, clean tree, behind, version greater than the latest tag), requires the version files to be bumped already and `GITHUB_ACTIONS=true`, attaches the draft to the existing tag (`gh release create --verify-tag`), and **stops at the draft**. Publishing stays a human click, the same boundary as the rest of the release.
- **The bump and the tag are separate steps.** `npm run release <version> -- --bump-only` runs the preflight and `verify`, bumps, commits and pushes `main`, builds nothing and needs no key, then prints the `git tag` command. The tag push is the trigger and stays the owner's outward action.
- **Workflow safety.** Trigger is `v*.*.*` tags and `workflow_dispatch` only. `permissions: contents: write` is the only grant. One concurrency group per version covers the tag push and the dispatch. Secrets appear only in the build step's `env`, never in a command line (`set -x` is absent, a test greps for it), and ref names and inputs reach shell code only through `env` (injection). The tagged commit must be an ancestor of `origin/main`. A local release's tag creation fires the workflow too; it detects the published release and does nothing. `npm run verify` is skipped in CI because `ci.yml` gates every PR and push; `src-tauri/target` is not cached so a signed release builds clean.
- **Tauri CLI:** the workflow installs the same CLI the preflight demands, pinned to one exact version (`TAURI_CLI_VERSION`, `>= 2.11.5`) that also keys the cache; the install is skipped only when `cargo tauri --version` equals it.
- **A gate job precedes the macOS job.** An ubuntu job (no secrets) resolves the version and checks whether the release is already published; the macOS job `needs` it and runs only when `skip != 'true'`, so a locally published release costs no 10x minutes.
- **Trust model (decision left to the user).** Secrets are repository-level and the actions are pinned by major tag like `ci.yml`. Running the build in an `environment:` with a required reviewer and pinning actions by SHA are optional hardenings, not applied.
- **Shipped containers are verified too.** After the built `.app`, the same `codesign`/`spctl`/`stapler` steps run on the app unpacked from the `.app.tar.gz` and on the app inside the `.dmg` (mounted read-only, detached in a `finally`). `neutralEnv` also drops legacy Tauri key names and any variable whose name looks like a credential (a deny-list: an allow-list would break git, cargo, npm and SSH locally). In CI a SHA-1 hash identity is refused (use the certificate name).

## Consequences

- Nothing here has run against Apple or GitHub Actions: the user's real certificate, API key, budget and a tag push are the acceptance tests. They are listed as manual checks in `docs/release.md` and the PR. Agents verify with unit tests and `--dry-run` only.
- **The identity switch** costs exactly one more Keychain re-prompt per item at the first Developer ID release, then none (the designated requirement is bundle id plus Team ID, so renewing the certificate keeps it). The ADR 007 note is updated accordingly.
- Apple silicon only, as in ADR 009. The DMG itself is not signed or notarized by this pipeline; Gatekeeper evaluates the notarized, stapled app inside it.
- A leaked repository secret is a leaked signing credential; the runbook lists rotation. Amended 2026-11-06 (public repository): the signing secrets, if stored in GitHub at all, go into an `environment:` with a required reviewer, and third-party actions are pinned by commit SHA. Writing the `.p8` to the runner's temporary disk is the one place a credential touches disk, on an ephemeral VM.
- `tauri-action` is not used, so Tauri-specific CI conveniences (matrix builds, automatic release body) are not available; Windows/Linux builds would need a different design anyway and are out of scope.
