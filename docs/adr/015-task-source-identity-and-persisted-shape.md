# ADR 015: Task source, task identity and the persisted shape

## Status

Accepted (#326, part of epic #264; decisions D1 and D2 of the epic). The ADR number was taken as the next free one on `main` and may be renumbered at merge.

## Context

Until now a board had exactly one task service (`boardConfig.taskService`: `local`, `example`, `notion`, `todoist`, `null`), and a task's id was whatever that service called it (the Notion page id). Epic #264 puts Local tasks and integrations on one board, which needs two things: every task knows its task source, and a task can later change source (move) without losing its history. Statistics, column order and positions, carry-over, the archive, timers, pending queues and routes are all keyed by `Task.id`.

## Decision

- **A task has an identity and a source (D1).** `Task.id` is the stable app-level identity and never changes. `Task.source` (`'local' | 'notion' | 'todoist'`) says where the task lives, `Task.externalId` (`string | null`) is the id its integration knows it by. For Notion-born tasks `id` equals the page id (so migrating existing data is the identity), for Local-born tasks `id` is generated (`generateTaskId()`) and `externalId` is `null`. A move updates `source` and `externalId` together in one store mutation; nothing keyed by `id` needs re-keying. Integrations receive `externalId`, never `id` (`externalIdOf()` throws for a Local task, which must never reach an integration). Rejected: source-only identity with a re-keying move (history loss across about nine keyed structures) and namespaced ids (`notion:<id>`, rewrites every key and route).
- **The persisted shape names sources, not a mode (D2).** `boardConfig.taskService` is replaced by `boardConfig.sources: { connected: Array<'notion' | 'todoist'>; default: SourceId } | null`. Local is implicit and never listed in `connected`; `null` still means "never onboarded". Credentials stay in `notionConfig` and the Keychain (ADR 007). Rejected: keeping `taskService` beside a new list (the old meaning lives in 40+ call sites).
- **Migration is one set of pure, idempotent normalisers in `lib/taskSources.ts`**, used by two paths so they cannot drift: (a) hydrate-time normalisation in `afterHydrate` of `board-store` and `tasks-store` (the only path on web, which has no envelope migrations), and (b) the desktop envelope migration 1 -> 2 (`migrateTaskSources` in `utils/dataFile/migrations.ts`; `CURRENT_SCHEMA_VERSION` and Rust's `SCHEMA_VERSION` bumped together, mandatory pre-migration backup per ADR 011, older builds open the file read-only per ADR 008). Mapping: `taskService: 'notion'` gives `connected: ['notion'], default: 'notion'` and tasks `source: 'notion', externalId: id`; `'todoist'` likewise; `'local'` and `'example'` give `connected: [], default: 'local'` and tasks `source: 'local', externalId: null`; `null` and anything unknown (the removed Linear) stay `sources: null`. A task without a source takes the board's default source of the time (`legacyTaskSource`), because before this change the board had exactly one. Pending deletes carried `service`; their snapshot's `source` replaces it. Hydration writes back only when a normaliser returned a new value (#273); the envelope step always rewrites `board-store`, which makes Rust rewrite an otherwise unchanged file at version 2.
- **Merging is per source.** `tasks.mergeTasks(source, fetched)` replaces only that source's tasks, matches existing tasks by `(source, externalId)` (`id` for Local), keeps the app-level `id` of a match, gives a new external task `id = externalId` unless that id is taken (then a generated one), and keeps its previous guarantees (local time tracking, timers, status locks, `deletedTaskIds`). Deleting a task records its `externalId` as well, so a fetch that knows the task only by that id cannot resurrect it.
- **Sync follows the task.** `useTaskSync` routes by `task.source` (not by the board mode) and passes `externalId` to Notion and Todoist, through the adapter registry (see "Source adapters" below).

## Consequences

- No visible change: a Notion-only or Local-only board behaves as before; a mixed board is not creatable yet (connect/disconnect is #320, move is #322). Until then a mode switch behaves exactly as before, in any sequence: a switch to Local turns the previous tasks into Local tasks (`adoptAsLocal`, pending deletes in their undo window included; nothing is written upstream any more), and a switch to an integration (`beginSourceSwitch`) makes it the only source, turns the other sources' tasks into Local tasks right away and sets the persisted one-shot marker `boardConfig.pendingSourceSwitch`. The first non-empty fetch of the new source, whichever call it is, replaces the other sources' tasks (`mergeTasks(..., { replaceOthers: true })`) and clears the marker; an empty or failed fetch leaves it set, and any change of `sources` clears it. During that replacement a Local task whose `id` equals a fetched `externalId` is that task, so a Notion -> Local -> Notion round trip keeps each task's `id` and local data. The marker is optional (absent = no switch pending), is kept by the hydrate normaliser only as `true` next to an integration default, and a board without it (such as the mixed E2E seed) is never replaced. Every other sync touches its own source only.
- Anything that builds a `Task` must set `source` and `externalId`; the type makes both required, so the compiler finds every constructor. Test fixtures use `tests/helpers/taskSource.ts`.
- Old exports import unchanged: web import replaces the stores and the next hydrate normalises them; desktop import hands the older envelope to Rust, which loads it and the webview migrates it like any other v1 file.
- A later schema change follows the same recipe: normaliser in `lib`, called from `afterHydrate` and from a migration step.

## Source adapters, multi-source fetch and per-source health (#318, epic decision D3)

- **One adapter per source.** `integrations/sources/` holds the `TaskSourceAdapter` interface (`fetchActive`, `create`, `update`, `remove`, `health`, plus the capabilities `syncsTime`, `archivesAsStatus`, `isConfigured`) and `LocalSource`, `NotionSource`, `TodoistSource`, thin wrappers over the integration classes. `composables/useTaskSources.ts` builds the adapter of a source from the current stores and configs; `useTaskSync` and `useIntegrationManager` ask it and never switch on a source name. An unconfigured source rejects with `SourceNotConfiguredError`, which `useTaskSync` reports with the old setup context (`notion_setup`, `todoist_setup`). `NotionIntegration` gained `fetchActiveBoardTasks()`, the throwing twin of `getActiveBoardTasks()`, so a failed fetch is not an empty list; `TodoistIntegration` still reports and swallows its own fetch errors (not wired as a second source before #320).
- **Fetch is per source and parallel.** `fetchTasks` fetches every connected integration (Local alone on a board without one) through `Promise.all` over independent pipelines: fetch, health, validation, merge. A failing source is marked in the health store (`offline` for a network failure, `broken` for a rejected or missing token, `degraded` otherwise), its tasks stay on the board, nothing is toasted and no setup dialog opens; the way back is the repair entry point of #319. The board's `lastSyncTimestamp` is the oldest successful sync among the connected integrations.
- **A stale result is dropped.** Each fetch holds a ticket: a newer fetch of the same source, or any change of `boardConfig.sources` (a disconnect, a switch, also to the same source) while it was in flight or waiting for the validation dialog, makes it stale, and a stale fetch merges nothing and writes no health (#326 N6). A pending source switch can therefore only be completed by a fetch of the new source.
- **Validation is per source** (`useSyncValidation`): only the fetched source's stored tasks count, Local never takes part, and the warning names the source. The warning state is module-level and queued, so the dialog the page renders is the one the manager awaits (#337); a newer warning for the same source replaces a waiting one.
- **Health persists per source.** `integration-health-store` is now `{ sources: Record<'notion' | 'todoist', { status, lastError, lastSuccessfulSync }> }` (Local has no entry: nothing upstream can fail). The old `{ notion, notionLastErrorReason }` is converted by `normalizeIntegrationHealthState` (`lib/integrationHealth.ts`) in the store's deserializer; the store writes back only when that changed something (#273). There is no envelope migration 2 -> 3: health is derived status that the next fetch relearns, an older build ignores the new key, and a bump would put every older build into read-only mode for it. Reconsider if health ever holds something that cannot be relearned.

## Pending-sync marker and sync status (#319, #336, #341)

- **The marker is state-based and lives on the task.** `Task.pendingSync?: { since, attempts, lastError }` says "the source does not hold this task as it is". It is set before a write (`markPendingSync`), cleared when the write succeeds (`clearPendingSync`), and persisted with the task, so it survives a restart. A transient per-task revision (never persisted) makes a change made while a push is in flight keep the marker. A Local task never has one (no upstream); a switch away from a source (`adoptAsLocal`) drops it. `pendingMove?: { fromSource, fromExternalId, toSource }` is the unfinished move of #322 (see "Move between sources"); the normaliser keeps it on any task, with or without a marker.
- **Pending time updates are one reason for it.** A timer tick still queues time in `pendingTimeUpdates` (keeping its `pending`/`syncing`/`failed` state, attempt count and error), but only for a source that stores time (`sourceSyncsTime`, Notion): a Local or Todoist task queues nothing, and `syncPendingChanges` drops any leftover entry of such a task instead of waiting for the 7-day cleanup (#336). `isSyncPending(id)` is "marker or queued time". A tick does not set the marker, so a running timer does not freeze the rest of the task against a fetch.
- **A fetch never overwrites unpushed changes.** `mergeTasks` keeps the local state of a task with a marker (and a task created while its source was unreachable, which has no `externalId` yet) and takes only the source's id; the push that follows clears the marker. A fetch of a recovered source ends with `syncPendingChanges(source)`; the periodic timer, the `online` event, a manual refresh and a stopped timer run it too.
- **A task made while the source is unreachable** (a network failure on create) is created locally with a generated `id`, `source`, `externalId: null` and a marker. The hydrate normaliser leaves its `externalId` null while the marker is there (a legacy task without a marker still gets `externalId = id`); the next push calls `adapter.create` and `completeCreate` stores the `externalId`. Deleting it before that sends nothing upstream.
- **Hydration writes only when something changed** (#273): `normalizeTasks` returns its input for a valid marker, repairs a half-written one (missing parts take neutral values), drops a marker on a Local task, and drops `sourceData`, the raw upstream object the integrations used to copy onto every task (#334; the mapping no longer sets it).
- **A failed write is the source's state.** `reportPushFailure` records the failure in the health store (`recordFailure`: offline, broken or degraded) and on the marker; the user hears about it once, on the way from fine to failing, and a source already known to be down stays quiet. The same call serves the fetch path and the tasks page's schema read (#341: `getDatabaseSchema(id, { report: false })`; only a rejected token or no connection counts, any other failure of that one read does not touch the source's health).
- **No dialog opens by itself.** `useErrorHandler` still marks a 401 or a `notion_setup` error as `broken` but no longer calls `triggerNotionSetup`. The sync button reflects the worst connected source (`broken`, then `offline`, then `degraded`; `sourceProblems`), its popover names every affected source, offers "Verbindung reparieren" (`repairRouteOf`: `/settings/notion` until #324; none for Todoist) and a retry. The card cloud (`useSavePending`) shows only while the card's source is not healthy and the task has unpushed changes, so a write in flight on a healthy source never flashes it. Cards show no other source state.
- **A Todoist reopen is replayed from the marker (#344).** The marker notes whether the source holds the task as completed (`pendingSync.upstreamDone`): set with the marker from the status before the first unpushed change, kept while the marker lives (a later change does not overwrite it), corrected by a push that left the marker standing and by a fetch. `pushTask` hands the adapter that note as `previousStatus`, so a Done -> Offen move made while Todoist was unreachable is reopened by the next sync, also after a restart, and an Offen -> Done -> Offen sequence never reopens a task Todoist holds as open. A marker written before #344 has no note and behaves as before.

## Connect and disconnect (#320)

- **Connect is not a source switch.** The one-source flows (welcome, Notion setup, Todoist OAuth: `beginSourceSwitch`) make an integration the only source, turn the other sources' tasks into Local tasks and set `pendingSourceSwitch`, so the first fetch replaces them. A connect (`useSourceConnections().connectSource`, `board.connectIntegration`) only adds: the integration joins `connected`, the default stays, no Local task is turned into anything, nothing is replaced, no prompt, and the new tasks join through the per-source merge (existing cards keep their order; the new ones are appended to their status column). It never sets the marker. The two meet in one corner, a connect while a switch is still pending (its source has not answered with tasks yet, possibly because its database is empty): the connect keeps the marker, and only the switch's own source (the default) can complete it; completing it replaces the Local tasks the switch adopted and leaves every other integration's tasks alone (`mergeTasks(..., { replaceOthers })` now drops Local tasks only). A never-onboarded board has nothing to connect to (the welcome flow picks the first source).
- **A connect is fresh.** `integrationHealth.resetSource` clears status, error and the last sync of an earlier connection before the first fetch, which is that source alone (`useIntegrationManager().fetchSource`; the other sources are not refetched and show no warning). If that fetch fails the connection stays and the source needs attention (#319); nothing is toasted.
- **Disconnect fails closed, in this order.** (1) The source's running timers stop (a timer's ticks are already queued as time, so the stop makes no new state: from here the time counts as an unsynced change before anything is discarded; the dialog counts a running timer as unsynced work). (2) With "Erst synchronisieren, dann trennen" the unsynced work is pushed first (queued deletes, then `syncPendingChanges(source)`, two passes because a push already in flight is skipped); anything left keeps the source connected (`sync-incomplete`), and the failure is the source's health, so the dialog then offers only "Trotzdem trennen" and "Abbrechen". (3) The credentials are reset with the Keychain delete awaited first (ADR 007; `notionConfig.clearConfig()`, a refusal keeps the source connected: `credentials`). (4) Only then one synchronous step (`tasks.disconnectSource`) removes the tasks, their column order and positions, carry-over, archive entries, queued time, operation versions, status locks, markers and pending deletes, and drops the source from `connected` (the default falls back to Local, a pending switch dies with its target). Statistics records stay: statistics ignore sources. "Unreachable" is `navigator.onLine === false` or a source that needs attention.
- **No orphans, no guards.** A pending delete that never reached the source is discarded with it, and so are its `deletedTaskIds` entries: the page still exists upstream, so a reconnect shows the database as it is. A disconnect is not a delete and adds nothing to `deletedTaskIds`. The undo toast of a discarded delete finds nothing to restore. A push that was in flight and fails after the disconnect neither toasts nor writes health for the gone source (`useTaskSync.isDisconnected`; a board without sources, such as most unit tests, has none to miss).
- **Reconnecting the same database is a fresh connect; a different database is a disconnect plus a connect.** The token and database come back through the setup (the disconnect removed them); tasks return with `id = externalId` again.
- **Local has no disconnect:** the store action takes an `IntegrationSourceId` only, the dialog is for integrations, and `disconnectIntegration('local')` is a no-op.

## Move between sources (#322)

- **A move is a local re-assignment now, an upstream create-then-remove after the undo window.** `tasksStore.reassignSource(id, target)` sets `source`, `externalId: null` and `pendingMove` in one mutation (an integration target also gets the marker), bumps the operation version and clears queued time; `id`, column, position, timer, tracked time and dates stay (everything is keyed by `id`). Nothing goes upstream while the undo toast is open (`holdMove`, not persisted): `runSync` and the flush leave a held task alone, a status change in the window is sent by the create after it. Undo (`restoreMoveOrigin`) makes no upstream call itself; a task that changed inside the window (`updateTask` while held: edit, status, tracked time; recorded in `heldChanged`, not persisted) comes back to an integration origin with the `pendingSync` marker, so the next flush sends it the change. Closing the app inside the window is not an undo: `commitPendingMoves` runs on start, on reconnect and at the start of every `syncPendingChanges`.
- **`commitTaskMove` keeps the safety order.** The target creates the page (`adapter.create(task)` with the task's current state; time spent and the completion date are written by one follow-up update, because the create does not carry them), then `completeMoveCreate` stores the `externalId` and drops a card a fetch made from that very page meanwhile, then the origin copy is removed through its own adapter (`fromExternalId`; a page that is already gone counts as removed). `pendingMove` with a null `externalId` means the create is outstanding, with an `externalId` the origin removal is queued; `clearPendingMove` ends it. A move to Local has no create, only the removal.
- **Failure classes follow #321.** A create the source refuses for good (400, 409, other 4xx) puts the task back (`restoreMoveOrigin`, nothing deleted) and raises `lib/taskMoveEvents`, which `useTaskMove` shows as "Verschieben fehlgeschlagen" with a retry. Offline, a source that needs attention, 401, 403 and 5xx keep the move pending with the reason on the marker and no toast.
- **A fetch must not duplicate a task mid-move.** `mergeTasks(source, fetched)` skips a fetched page whose `externalId` is the `fromExternalId` of a task whose move leaves `source`, never matches a fetched page to a moved task whose page is not created yet, and keeps the earlier of the local and the fetched `createdAt` (Notion and Todoist stamp their own creation time on the new page).
- **Delete during a move** also removes the origin copy (`deleteTaskUpstream`, `originToRemove`); a delete that wins the race against the create removes the page the create just made. An origin whose source was disconnected meanwhile just ends the move.

## Trash (#422)

- **kan-do owns the trash for every source.** `store/trash.ts` (`trash-store` in `PERSISTED_KEYS`) holds `entries: TrashEntry[]` (`types/trash.ts`: `taskId`, the `task` snapshot with `timerId: null`, `deletedAt`, `fromStatus`, `carryOver`), newest first, at most 100 and 30 days (`lib/trash.ts`, purged on add and on hydrate; hydrate persists only when it purged, #273). The shape is additive: a state without the key hydrates to an empty trash, no schema bump and no migration. Export/import carry it; an imported entry of a source that is not connected fails its restore with the normal error and stays. `disconnectSource` leaves the source's entries in place.
- **The upstream delete is unchanged.** It runs when the undo window closes (Notion archives the page, Todoist deletes the task, Local has nothing upstream). The trash entry is made at that moment, also when the commit is queued offline (`useTaskDeletion.closeDelete`); a commit that fails for good restores the task to the board and removes the entry. A reload inside the window closes it the same way (`resumePendingDeletes`).
- **The window has no toast.** `useUndoWindow.beginTimed` (with `pause`/`resume` and reactive getters) runs it; the toast mode stays for Move. `PendingTaskDelete` gains `fromStatus` and `slot { afterId, height }` (old persisted deletes without them commit as before and render no gap); the column renders a `TaskDeletedGap` from it (`utils/columnItems.placeGaps`), never a sortable.
- **Restore goes through the source first.** `TaskSourceAdapter.restore(task)`: Local re-adds, Notion un-archives the same page and writes the snapshot onto it (`PATCH /pages/{id} { archived: false }`, own proxy route `unarchive-page`; a 404 creates a new page), Todoist creates a new task (new `externalId`, the app `id` stays, so statistics, order, carry-over, archive state, timers and routes keyed by `id` survive; comments and other data kan-do never stored are not restored). Only then, in one synchronous step, `undeleteTask`, add to the board, `restoreGuard`, carry-over and the entry's removal. A delete that is still queued (never reached the source) is cancelled instead: no upstream restore call.
- **`restoreGuard` (transient) protects a fresh restore from a stale fetch.** `mergeTasks` keeps a guarded local task that a fetch started before the restore does not contain, and matches it normally when it does; the guard ends once a merge contains the task or after 60 s. A trashed task stays in `deletedTaskIds` until its restore, so no fetch brings it back.
- **A task from Jetzt is restored into Offen**, never into Jetzt (WIP limit); an undo inside the window returns it to Jetzt only while Jetzt is free.
