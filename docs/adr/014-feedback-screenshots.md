# ADR 014: Feedback screenshots (native snapshot, canvas annotate, feedback-assets upload)

## Status

Accepted (#247, follow-up of [ADR 010](010-in-app-feedback.md), part of epic #221). Replaces the DOM rasterisation that failed in ADR 010's spike.

## Context

The epic asks for an annotated screenshot in a feedback report. ADR 010 shipped context and element pick without it because `modern-screenshot` drew hard grey shadows, dropped an open `UModal` and took 3.9 s in WKWebView. The privacy rules of #227 stay binding: opt-in per report, preview, redaction before upload, nothing automatic, memory only.

## Decision

- **Native snapshot over DOM rasterisation and over Screen Recording.** `feedback_capture` (`src-tauri/src/capture.rs`) asks the app's own `WKWebView` for `takeSnapshotWithConfiguration:completionHandler:` through `WebviewWindow::with_webview` (main thread, completion handler bridged to async with a one-shot channel, 10 s timeout, 12 MiB cap, typed errors `Timeout`/`TooLarge`/`Failed`/`Unsupported`) and returns the PNG as raw binary IPC. WebKit renders what it shows, so shadows, `UModal`, teleported content and Figtree are exact, with no permission prompt. `SCScreenshotManager`, `CGWindowListCreateImage` and `CGRequestScreenCaptureAccess` are not used anywhere: they need the Screen Recording consent, and DOM rasterisers share the WKWebView limits that failed. The one `unsafe` block lives in one function with a safety comment; `objc2`, `objc2-foundation`, `objc2-app-kit`, `objc2-web-kit` and `block2` are direct dependencies at the versions already in the tree (Tauri/wry), with `default-features = false` so the lockfile gains no package. Spike result on `tauri dev` (seeded board, 1200x800): not blank, Figtree, radius and soft shadow, open day-close modal, Jetzt card and Erledigt column present, 10 to 33 ms per capture, no prompt.
- **The mask is applied to the live DOM for the instant of the capture.** The native snapshot has no clone to edit, so `html.kando-capture-mask` (rule in `assets/css/utilities.css`, CSS variables only) hides `[data-private]` text behind the ink token. It is set after the dialog has left and two animation frames passed, and removed in `finally`, also on error and timeout. `data-private` sits on task title, notes, topic, activity and custom property values (card, current-task variant, stack caption, task sheet, add form, day-close list, "Gestern geschafft", topic statistics); the activity rows of the task sheet and the add form were missing it until #704, and `tests/e2e/feedback-mask.spec.ts` now walks every rendered text node holding a seeded title, topic or activity (board ungrouped and grouped by activity and topic, task sheet) and fails on any glyph the mask leaves visible; `TaskPropertyRow` has a `private` prop for its value column, so no new wrapper surrounds a sortable (DnD invariants stay). The toggle "Aufgabentexte schwärzen" is on by default and re-captures. A missed field is the residual risk: the review preview and the Schwärzen tool are the backstop.
- **Redaction is an opaque fill, no blur.** Marks (Rechteck, Pfeil, Schwärzen, undo last, clear) are drawn on a `<canvas>`; "Fertig" flattens them at most 1600 px wide and re-encodes with `canvas.toBlob`, which burns redactions in and drops all metadata. The raw capture and the strokes are dropped from memory then, and on cancel, discard and send. Capture, strokes and flattened image live in module memory only: never storage, never a persisted store, never the data folder.
- **Canvas-only CSP stance.** The image only ever lives in `ArrayBuffer`, `ImageBitmap`, `<canvas>` and `Blob` (`createImageBitmap(Blob)`, `canvas.toBlob`, `ClipboardItem`). No `<img>` with a blob or data source and no object URL, so `img-src` stays `'self'` ([ADR 012](012-desktop-csp.md) unchanged). A Vitest guard fails on an `<img>` with `blob:`/`data:`, `URL.createObjectURL`, `new Image(` or `fetch(` in the feedback code. Checked in the real WKWebView under the dev CSP (`img-src 'self'`): the IPC answer arrives as `ArrayBuffer`, `createImageBitmap`, canvas draw and `toBlob` work, no `securitypolicyviolation`. The built bundle (`tauri build`) is a manual check; if it blocks the canvas path, add `blob:` only (never `data:`) to `img-src` in both `csp` and `devCsp` and update `tests/config/tauri-csp.test.ts` and ADR 012 in the same change.
- **Upload to an orphan `feedback-assets` branch through the Contents API.** Order: `GET git/ref/heads/feedback-assets`; on 404 create the branch (`POST git/blobs` README, `git/trees`, `git/commits` with `parents: []`, `git/refs`; a 422 on the ref means another report created it first); `PUT contents/feedback/<yyyy>/<mm>/<uuid>.png` with `branch: "feedback-assets"` (a new uuid per image, so never an overwrite and no `sha`); then `POST issues` (label `inbox`) whose body embeds the image (`blob/feedback-assets/<path>?raw=true`, viewable for repo members; for everyone once the repository is public), the plain path and a `gh api` hint for agents. The path is fixed when the image is flattened, so the review shows the exact body; `assetPath` is remembered after the `PUT`, so a retry after a later failure never uploads twice. A PNG whose base64 body would exceed the 10 MiB cap is shrunk step by step before it is refused.
- **Retention.** The branch grows without cleanup. Images are small (one flattened PNG per report, at most 1600 px wide). The repository was private when this was decided; since it is public (2026-11-06, [ADR 010](010-in-app-feedback.md) amendment) the branch and every image on it are public too, and only the owner's token uploads (everyone else pastes the image into their own issue). Nobody deletes them automatically; a manual cleanup of the branch is always possible. Cleanup and protection are out of scope here.
- **Contents: write on a token that cannot be scoped per branch.** Fine-grained tokens grant Contents per repository, not per branch, so the feedback token (Issues: write, Contents: write) could in principle write `main`. Mitigations in the app: the token lives only in the Keychain and never reaches JS ([ADR 007](007-secrets-keychain.md)); the host and repository are pinned in Rust; and, decided with the owner, **`github_request` refuses every write of the feedback entry except `POST /issues`, `POST git/blobs|trees|commits`, `POST git/refs` with `ref = refs/heads/feedback-assets`, `PATCH git/refs/heads/feedback-assets` and `PUT contents/<path>` with `branch = feedback-assets`** (an absent branch means the default branch, so it is refused too). Merges, other refs, tags and branch renames never get through, and a refused request never reads the Keychain or touches the network (`github::validate_feedback_write`, unit-tested). **Residual risk, accepted:** this pin constrains the app, not the token. Someone who extracts the token from the Keychain (a process running as the user that is allowed to read the item, or a user approving a prompt) can push to `main` of the private repository. A ruleset protecting `main` would close that; the owner pushes to `main`, so it stays a choice and is not part of this change.
- **Upload probe in Settings.** Saving a token still checks read only, and a token without Contents is accepted for text reports. The feedback row gets "Screenshot-Upload prüfen": `POST git/blobs` with an empty body creates an unreferenced blob, which needs Contents: write but leaves no commit, no ref and nothing visible. 2xx means the upload is allowed; a 404 or a permission 403 says the token lacks Contents: write and screenshots then go to the clipboard. The result lives in memory on the row (`useGithubTokens`), is never stored, and a positive result clears a remembered refusal of the dialog.
- **Fallbacks (D5-C).** A 404, or a 403 whose message names the missing permission ("Resource not accessible…"), from the branch check, the bootstrap or the `PUT` stops before any issue exists, keeps the draft and the image, remembers `uploadDenied` for the session (reset when the token changes) and turns the primary action into "Ohne Bild senden": it copies the PNG with `navigator.clipboard.write` first (the user gesture), then creates the issue without the image section and with a paste line. Without a token, or after a 401, the prefilled link opens and the PNG goes to the clipboard; a clipboard failure is shown and the link still opens. Offline, 5xx and rate limit keep the draft with "Erneut versuchen"; GitHub answers primary and secondary rate limits with 403 too, so a 403 with a rate-limit message, or with no recognisable message (proxy, captive portal), counts as a rate limit (`lib/feedback/uploadAccess.ts`) and never disables uploads. The same classifier decides the Settings probe. A failed re-capture rolls "Aufgabentexte schwärzen" back to how the image on screen was taken, and the capture's frame wait times out (2 s) instead of hanging the hidden dialog. Nothing leaves without the click on the primary action.

## Consequences

- The author must add Contents: write to the feedback token on GitHub before the upload works; until then the probe says so and screenshots use the clipboard.
- `feedback_capture` is macOS-only (other targets answer `Unsupported`); the web build has no feedback at all.
- Drawing needs a pointer; the keyboard path is to leave the annotate step ("Zurück") or rely on the default mask. This is a documented limit, not a defect.
- ADR 010's spike section is superseded for the screenshot part; ADR 012's `img-src`/`font-src` rows lose the "deferred" wording; ADR 007 names the probe.
