# ADR 007: Secrets live in the macOS Keychain

## Status

Accepted (#223, part of epic #221)

## Context

API tokens (Notion, Todoist) sat in `localStorage` next to the task data. The desktop app is about to keep its data in a user-chosen, possibly cloud-synced folder (#222) and to call GitHub for updates (#225) and feedback (#227) with fine-grained tokens, one of which can write contents. Tokens must never reach `localStorage`, the data folder, logs or feedback reports. The WebView runs with `csp: null`, so any script that runs in it must be assumed able to call any IPC command it is allowed to.

## Decision

- **One Keychain-backed store, in Rust** (`src-tauri/src/secrets.rs`): `keyring-core` with `apple-native-keyring-store` (the `keyring` crate's v4 split), macOS only (`cfg(target_os = "macos")`). Other targets answer `Unsupported` and the frontend behaves like the web build. Entries live under service `com.julius.kan-do` (the bundle identifier, which must not change) with the fixed accounts `notion-token`, `todoist-token`, `github-updates`, `github-feedback`. Any other name is refused.
- **Write-only GitHub entries (direction B).** `secret_get` returns only the Notion and Todoist tokens, because their client code needs the string. The GitHub tokens cannot be read back by JS: it can `secret_set`, `secret_delete` and ask `secret_status` (`present`, last four characters, `rejected`). A pinned command, `github_request(entry, method, path, body?, token?)`, makes the calls: host `https://api.github.com` and repository `jaylouiz/kan-do` are constants in Rust, paths with `..` (plain or percent-encoded), other repositories or absolute URLs are refused, only GET/POST/PUT/PATCH, 10 s timeout, 10 MiB body cap, no redirects, `Authorization`/`Accept`/`User-Agent` set in Rust. The optional `token` is a candidate used instead of the stored one, to check a new token before it replaces a working one: it needs no stored token, ignores the `rejected` flag, never sets it and is never stored by this command. There is deliberately no `http:default` allow-list entry for GitHub. The feedback entry's writes are further pinned to issues and the `feedback-assets` branch, and Settings can probe whether the token may write contents (`POST /git/blobs` with an empty body, which leaves nothing in the repository; ADR 014). Rejected alternatives: A, one store where JS reads every entry (smallest, but any webview script could read the Contents-write token while `csp` is null); C, additionally a Rust Notion proxy (rewrites a working integration).
- **`rejected` flag.** A 401 sets an in-memory flag for that entry; `github_request` then fails fast without a network call until a new token is saved or the entry is removed. This gives one calm notice per entry per session. Each `set` and `delete` bumps a per-entry epoch, and `github_request` flags only if the epoch is unchanged since it read the stored token (`mark_rejected_if`), so a late 401 for an old token cannot flag a token saved in between (#245 L4). Rust consumers use `secrets::get(app, entry)` and `secrets::mark_rejected(app, entry)` (#225's updater).
- **Missing is not an error and an error is not missing.** `secret_status` returns `state: "ok"` with `present`, or `state: "error"`; `secret_get` returns `null` for a missing entry and rejects for a Keychain failure (denied, locked, unavailable). Errors are fixed strings: platform error text can carry the raw secret bytes and is never forwarded. The last four characters are cached in memory after the first read.
- **`SECRET_STATE_PATHS`** (`lib/secrets.ts`): `notionConfig.config.token` and `board-store.boardConfig.todoistApiToken`. On desktop both stores omit these paths from persisted state (`persist.omit`). The omit arrays are live and start empty: the bootstrap arms the omission per path once the Keychain holds the token or there is nothing to migrate, so no store write that runs before the bootstrap (such as `board.ts` afterHydrate `$persist()`) can strip a legacy token unread; the in-memory `config.token` / `todoistApiToken` stay, so the existing call sites do not change. Everything that serialises app state (#222 data file, #224 export/import) must exclude these paths. On web nothing changes.
- **Reads at start-up, not lazily per call.** `plugins/secrets.client.ts` awaits the Keychain read for Notion and Todoist before mount, so `isConfigured` is right on the first render. The GitHub entries are read lazily, only when the settings page or a Rust consumer needs them, to limit Keychain prompts.
- **One-time migration** (`lib/secretsBootstrap.ts`): a token found in persisted state with an empty Keychain is written, read back and compared, and only then removed from the stored blob. If both exist the Keychain wins and the stored copy is stripped. A Keychain failure leaves the stored token in place and working (its omission is never armed, so later writes keep it), shows one notice, and retries on the next start. A locked Keychain with no stored copy does not route the user to setup. An unexpected throw fails closed (#245 N4): each entry runs in its own `try/catch`, a throw arms that entry's omission, yields `error` (counts as failed, applies a legacy copy if one was read, else the entry is `unavailable`) and never skips the other entry; if `plugins/secrets.client.ts` still sees a throw it arms every omission and shows the same notice, and the app boots. The legacy copy is never deleted on these paths. The writer in `appStorage` (ADR 008) stays the primary guard; this is defence in depth.
- **Saving.** The Notion wizard and settings write the Keychain before the config counts as saved. A GitHub token is checked first, as a candidate, with a read-only call (`updates`: `GET /releases`, `feedback`: `GET /issues`), and stored only if GitHub accepts it, so a failed check leaves a working token untouched. Only a 401 means "rejected"; any other non-2xx answer (403, 404, 5xx) or a network error is "could not check" and never deletes a stored token. Write scopes cannot be tested without writing; a later 401 shows the rejected notice. Resetting the Notion integration awaits the Keychain delete and keeps the config if it fails. Removal is immediate, with an undo toast; the Keychain delete runs after the toast closes (closing the app inside that window leaves the token stored).
- **Todoist OAuth is web only.** The token exchange (`middleware/todoistOAuth.ts` → `/api/todoist/token`) needs the Nitro route and a server-held client secret, so it is web/node-server only and the middleware does nothing on Tauri. The desktop app never exchanges an OAuth code; its Todoist token would come from the user pasting a personal token into the `todoist-token` entry (undecided, #260).
- **External links** open in the system browser through `tauri-plugin-opener` with a narrow permission (`https://github.com/settings/**`, `https://www.notion.so/my-integrations`).

## Consequences

- **Ad-hoc signing re-prompts.** The macOS Keychain ties an item's access to the app's code signature. With ad-hoc signing every update has a new identity, so macOS asks once per entry after each update; `tauri dev` has a separate identity and prompts too. A stable signing identity fixes it: with Developer ID signing ([ADR 013](013-signing-notarization-and-ci-release.md), #228) the first such release changes the identity once, so macOS asks one last time per entry (*Always Allow*), and updates after that no longer prompt. `tauri dev` keeps its own identity and still prompts. Reading GitHub entries lazily keeps the number of prompts low.
- The webview can still read the Notion and Todoist tokens through `secret_get`. That is accepted: the clients need the string, and a Rust proxy for them is out of scope.
- The `secret_*` and `github_request` commands are `async fn` but call the Keychain synchronously, so a Keychain prompt blocks one runtime worker until it is answered. Accepted: the runtime is multi-thread and at most four entries exist, so at most four workers can wait (#245 L5; `spawn_blocking` is not worth the churn).
- Token values never appear in logs, errors, command results (other than `secret_get` for Notion/Todoist and the last four characters) or panic messages; `cargo test` covers the allow-list, the read-back refusal, missing vs error, the `rejected` lifecycle and the path pinning.
