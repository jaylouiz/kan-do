# ADR 019: Bundle identifier `io.github.jaylouiz.kan-do` and the identifier migration

## Status

Accepted (#42). Amends [ADR 007](007-secrets-keychain.md): the identifier no longer "must not change"; it may change when the migration below runs.

## Context

Releases up to 0.11.0 shipped with the identifier `com.julius.kan-do`, a domain the project does not own. A GitHub-hosted project without its own domain uses the reverse-DNS form of its handle, `io.github.jaylouiz.kan-do`. macOS keys the app's folders on the identifier (`~/Library/Application Support/<id>`, `~/Library/Logs/<id>`, the web view's `localStorage`) and kan-do reuses it as the Keychain service (ADR 007), so an update under a new identifier would start an empty app: no tasks, no `data-location.json`, no backups, no tokens, and the old data would sit unreachable next to it. Decision D1 on #42: migrate in-app.

## Decision

- **The identifier is `io.github.jaylouiz.kan-do`** (`src-tauri/tauri.conf.json`); `secrets::SERVICE` equals it and a Rust test compares both.
- **A Rust module runs two steps in `setup`**, after the log plugin and before `DataFile` is managed (`src-tauri/src/identifier_migration.rs`). Windows exist before `setup` but nothing is served before the event loop runs, so no command sees the pre-migration state. In Rust, not in the webview: Rust owns both stores, and a JS-driven migration would need new IPC commands and race the hydration.
- **Data step: copy, verify, never touch the old folder.** The legacy folder is the sibling `com.julius.kan-do` of the new directory. `backups/*` and `kan-do-data.json` are copied first, the pointer last, each file through the app's atomic writer and compared by SHA-256 after writing. The pointer keeps its `deviceId` (a new one would make every file a "written by another device" conflict, ADR 011); when it named the legacy default folder it names the new default folder, when it named a custom folder it is copied byte for byte and nothing else moves (data and backups live in the custom folder). A data file without a pointer is copied and adopted by the next load, as ADR 008 already does. The legacy folder is never written, moved or deleted: it is the downgrade path and the user removes it by hand when satisfied. `identifier-migration.json` in the new config dir records `in-progress` / `done` / `skipped` (states only, no values).
- **Idempotent and never mixing.** `done` or `skipped` stops later runs. A new folder that already holds data and has no `in-progress` marker is `skipped`, never merged. While `in-progress` the destination files are the migration's own: a stale copy from an earlier failed run (after which the app ran on the legacy folder and changed it) is replaced, so the retry carries the newer data.
- **Failure never becomes a first run.** Any copy, verify or marker error, and an unreadable legacy pointer, make `DataFile` use the legacy directories for that session (the previous version's behaviour, including its `read-only-corrupt` for a bad pointer) and retry at the next start. Without it the webview would find no pointer and no file, import an empty `localStorage` and create an empty data file, with the real data one folder over.
- **Keychain step: move per entry.** For each of the four accounts, the new service is checked first: a value there → the new one wins and the legacy entry is not even read (no prompt for it); otherwise nothing under the legacy service → resolved; otherwise write the new entry, read it back, compare, and only then delete the legacy one (a refused delete is logged and ignored). A Keychain error (a denied prompt) or a mismatch leaves the entry unresolved and writes no marker, so the next start retries, but only for 3 starts (`secretsAttempts` in the marker, no value): after that the step gives up and the legacy entries stay, so a denial is not asked again at every start; the user re-enters the tokens in the settings (no notice, no setup routing: the existing bootstrap rules of ADR 007 apply). All four resolved → `secrets: done`, and the legacy service is never read again. Fresh installs resolve to done in four no-entry reads (no prompt).
- **The Keychain step runs only for the production identifier.** The Keychain service follows the running identifier (`secrets::service_for`), so a sandbox identifier has an empty service of its own; a `…sandbox-<port>` run (`docs/testing/tauri-dev-sandbox.md`) skips the step so it can never read or create real entries. The data step runs for any identifier, so the sandbox can verify it with a seeded legacy folder under the throwaway `HOME`.
- **Release builds only (for the production identifier); debug builds keep the legacy identity (D8).** `tauri dev` and debug builds carry the production identifier too. Running both steps there would move the installed 0.11.0's tokens away and mark the migration done ahead of the real update; using the new, empty folder would make the dev run write the first data there, and the release would then find a populated destination and record `skipped`, stranding the real data in the legacy folder. So `run_gated` makes a debug build with the production identifier behave exactly as before the rename: the legacy folder is its data folder (`Dirs` point at the legacy sibling, the new folder is never created or written) and `secrets::service_for(true, <production identifier>)` keeps the legacy Keychain service. Any other identifier is its own Keychain service (a sandbox run never touches a real entry, kd#54). The first release build is the only thing that migrates, and it copies whatever the legacy folder holds by then (including what dev runs wrote). A `…sandbox-<port>` identifier still runs the data step against its throwaway `HOME`; its Keychain step is skipped. Accepted: a dev run reads and writes the real legacy folder, as `npm run tauri:dev` always did; a separate dev identifier was rejected because it would silently change what the maintainer's dev runs show.
- **Not migrated:** the web view's `localStorage` (`kando-locale`, `statistics-backfill-state`), logs and caches. The language falls back to `navigator.languages` then German; the backfill job re-checks once and is idempotent (ADR 008). The old logs stay in `~/Library/Logs/com.julius.kan-do/`.
- Logging: one line per step with outcome and counts, never a path with user content, never a value.

## Consequences

- **Keychain prompts.** The legacy items belong to the old code identity, whose designated requirement names the old bundle id, so reading and deleting each present entry may prompt once (up to eight prompts at the first start; *Always Allow*). With ad-hoc signing macOS asks after every update anyway (ADR 007, ADR 013); the first Developer ID release has its own one-time identity switch, which coincides with this one if both land together. The number of prompts is `unverified` until a release is tried on a Mac with 0.11.0 installed (`docs/release.md` checklist).
- **Downgrade:** the old app finds its data folder (still there) but no tokens (moved) and not the edits made since the update.
- **Privacy permissions:** macOS treats the bundle as a new app, so access to a custom data folder in iCloud Drive or Documents may be asked again.
- **Updater, signing, notarization:** the updater replaces `kan-do.app` in place and verifies the minisign signature, which does not involve the identifier; the updated bundle carries the new `CFBundleIdentifier`, which is what starts the migration. Code signing derives the signing identifier from the bundle id, so `codesign -dv` must show the new one (release checklist). Nothing in the release script or ADR 013 pins the identifier.
- `cargo test --lib` covers both steps with temp directories and in-memory backends: copy, custom pointer, no pointer, idempotence, resume, skipped destination, failed copy, unreadable pointer, legacy folder byte-identical in every case, moved/absent/kept-new/mismatch/read-error/refused-delete entries, the production gate and that no value reaches the marker.
