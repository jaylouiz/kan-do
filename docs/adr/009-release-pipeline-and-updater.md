# ADR 009: Release pipeline and self-updater from GitHub releases

## Status

Accepted (#225, part of epic #221). Amended 2026-11-06 for the open-source publication: the repository is public, the update token is optional (see "Token custody").

## Context

The desktop app is used daily and must update itself. The repository is private (epic decision D2: private repo plus a Keychain token), Actions minutes are out of budget (D3: a local release script), and Apple signing is ad-hoc. The updater therefore has to fetch its manifest and bundle from the GitHub API with an `Authorization` header, which `tauri-plugin-updater` can do only through its builder. Since the open-source publication (2026-11-06) the repository is public: `releases/latest` and its assets are readable without a token, so the header is sent only when a token is stored.

## Decision

- **Direction A: `latest.json` is a release asset.** There is no static manifest URL (private repo, asset ids change per upload), so `tauri.conf.json` configures **no endpoint**, only `plugins.updater.pubkey`. `update_check` (Rust) calls `GET /repos/jaylouiz/kan-do/releases/latest` through the pinned GitHub client from #223, picks the asset named exactly `latest.json`, builds `https://api.github.com/repos/jaylouiz/kan-do/releases/assets/<id>` **from the numeric id** (never from a URL in the response) and hands it to `updater_builder().endpoints([url])`. The plugin fetches the manifest (GitHub answers with a 302 to signed storage), compares versions, verifies the minisign signature and downloads the bundle from its API asset URL. Bundle URLs in `latest.json` are API asset URLs, not `browser_download_url`.
- **Rejected: B** (manifest on a dedicated branch: two sources of truth, and the `Accept: application/octet-stream` header would leak into the manifest fetch) is the **documented fallback**, to be taken only as a decision if the real first update shows the plugin cannot parse the manifest from the signed-storage response. **Rejected: C** (own updater instead of the plugin: signature verification and the `.app` swap are not ours to rewrite). Manifest URL and headers live in two small functions (`manifest_url`, `engine_headers`) so B stays a local change.
- **Header handling.** `Accept: application/octet-stream` (and `Authorization: Bearer <token>` when a token is stored) are set **once on the builder**. The plugin applies builder headers to the manifest request and to the bundle download (and only defaults `Accept` when none is set), so one header set serves both. reqwest drops `Authorization` on the cross-host redirect to signed storage, which the signed URL requires. The token is marked sensitive and appears in no log, event, result or error string (a Rust test feeds a recognisable token and searches every output). No builder timeout is set: the plugin would apply it to the whole bundle download. The manifest request is capped with a 10 s `tokio::time::timeout` instead.
- **Rollback and bundle host.** `plugins.updater.requireSignedVersion` is `true`: the plugin refuses a bundle whose signed (trusted-comment) version differs from the version `latest.json` announces, so a crafted manifest cannot pair a new version number with an older, validly signed bundle; the default comparator already installs only strictly newer versions, and `allowDowngrades` stays off. The release script refuses to publish a signature without the version. The bundle URL in `latest.json` is attacker-influenced input that receives the `Authorization` header, so `run_check` keeps an `Update` only when its `download_url` is exactly `https://api.github.com/repos/jaylouiz/kan-do/releases/assets/<digits>` (otherwise `manifest-invalid`); a Rust test pins the config and the URL shape.
- **Token custody.** The `github-updates` token is read natively (`secrets::get`), once per check; JS never sees it and has **no `updater:*` permission** in `capabilities/default.json`, so it can neither call the plugin nor set endpoints. The token is **optional** (amended 2026-11-06, public repository): without one, `run_check` requests `releases/latest` unauthenticated through `github::get_public` (same path pin, timeout, no redirects, body cap) and the builder gets no `Authorization`. GitHub allows 60 unauthenticated API requests per hour and IP, plenty for one check per launch; a stored token (the maintainer's) is still sent and only raises that limit. With a token, 401 (and a 403 that is not a rate limit) marks it rejected for the session (`secrets::mark_rejected`), later checks fail fast without a network call until the token is replaced or deleted. Without a token nothing can be rejected: every 403 is a (secondary) rate limit. 429, and 403 with `x-ratelimit-remaining: 0`, are `rate-limited` ("try later") either way. 404 means "no release yet" (or a token without access) and never marks the token. The former `no-token` status is gone; the placeholder public key answers `not-configured` and never panics.
- **Install order** (`update_install`, stops at the first failing step with a typed error, no restart): data guard (refuse when the data file is in `missing-file`, `write-failed` or `read-only-corrupt`; `read-only-newer-schema` is allowed because updating is the cure; #224 adds `conflict`) → `data_flush` → pre-update backup (**hook only until #224 is merged**, see the TODO in `AppSteps::backup`) → `download_and_install` with `update://progress` events → flush again and relaunch: on macOS the app quits through the normal event loop exit (`app.exit(0)`, so `RunEvent::Exit` flushes) and a detached helper (`src-tauri/src/relaunch.rs`) opens the bundle without `-n` once the old process is gone, so two instances never overlap and no orphaned Dock icon is left (#276); `app.restart()` stays the fallback outside an .app bundle and on other platforms. The webview calls `useDataFolder().flushNow()` first to drain its own queued writes. A failed download or signature check leaves the installed app untouched (plugin behaviour). A migration needed by the new version runs on the next start through #222's chain with its own backup.
- **Release pipeline** (`npm run release <version> [-- --dry-run] [--skip-verify] [--skip-e2e]`, local): preflight with one message per refusal, `npm run verify` and the full E2E suite before the build (#355), targeted version bump of four files (`package-lock.json` only in its two root `version` fields, no npm run; amended 2026-11-03 after the untouched lock drifted one version behind and dirtied the tree on every install), signed `tauri build`, then an **atomic draft publish**: push the bump commit, create a *draft* release on it, upload bundle, signature and dmg, read the asset ids back, write and upload `latest.json`, verify all four assets are `uploaded` and non-empty, and only then publish (`--latest`, which creates the tag). `releases/latest` ignores drafts, so a half-published release is never visible to installed apps. A failed run leaves at most a draft; the same command replaces it and accepts an already-bumped tree. Helpers are pure (`scripts/release/*.mjs`) and unit-tested; `--dry-run` bumps a temp copy, prints every command and needs no key. npm swallows `--dry-run` without a `--`, so `npm_config_dry_run` is honoured as a dry run.
- **Key custody.** The updater signing key is generated by the user, stored in the Keychain (`kan-do-updater-key`, password `kan-do-updater-key-password`) or the environment and backed up a second time. The script hands it to `tauri build` through the child environment and never prints or writes it; agents never touch it and never run a real release. Losing it strands installed apps (they cannot verify updates), which `docs/release.md` states before the user generates it.
- **Log file.** `tauri-plugin-log` is registered in all builds with the `LogDir` target (`~/Library/Logs/io.github.jaylouiz.kan-do/kan-do.log`), five rotated files of about 1 MB, `Info` in release and `Debug` in dev. Update steps log status names, versions and error kinds only.
- **Frontend.** `useAppUpdater` wraps the three commands; `/settings/updates` (desktop only) shows version, every state and the log folder; `UpdateDialog` installs after confirmation and cannot be closed while it runs; one silent check per launch about 10 s after mount, a once-per-session toast only for an update; two desktop-only palette commands. The notes hook for #226 is `getUpdateNotes()` (returns `null`) and `loadReleaseNotes()`.
- **Keychain re-prompt.** Ad-hoc signatures change with every build, so macOS asks again for Keychain access after each update (and under `tauri dev`). Expected; the runbook says to choose *Always Allow*. Developer ID signing ends it after a one-time identity switch (ADR 013).

## Consequences

- The first real N to N+1 update is the proof of the one detail verified only on paper: that the plugin parses `latest.json` from the signed-storage response. If it cannot, issue #225 goes back to the owner and B is chosen deliberately.
- Every installed app checks for updates, with or without a token (amended 2026-11-06; before the publication a user without the `updates` token never got a check).
- Apple silicon only; no Intel, Windows or Linux, no channel other than `stable`, no skip-version. Notarization (Developer ID) and a CI release are optional additions: [ADR 013](013-signing-notarization-and-ci-release.md).
- The release is only as safe as the signing key and the repository's release permissions; both are documented in `docs/release.md`.
