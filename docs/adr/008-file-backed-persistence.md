# ADR 008: File-backed persistence on desktop

## Status

Accepted (#222, part of epic #221)

## Context

All persisted store state lived in WKWebView `localStorage`: invisible to the user, not relocatable, not covered by any backup, and lost with the webview data. The desktop app is used daily, so the data has to be a readable file in a folder the user can choose (for example a cloud-synced one) and has to survive restarts, updates and quitting mid-edit. The web build keeps `localStorage`.

## Decision

- **Rust owns the file and the write path** (`src-tauri/src/data_file.rs`, direction A of the #222 options). It keeps the authoritative in-memory copy of the `stores` map, writes it debounced (400 ms trailing, 2 s max wait so a ticking timer cannot starve it) and atomically (temp file `.kan-do-data.json.tmp*` in the same folder, fsync, rename, fsync of the directory), and flushes synchronously on window close, `RunEvent::ExitRequested` and `RunEvent::Exit`. Rejected: JS-owned cache with an exit handshake (a Cmd+Q that does not fire `onCloseRequested` loses the last edits), and `plugin-fs`/`plugin-store` (no fsync + rename, scope widened at runtime).
- **The webview keeps a synchronous mirror** only for the `pinia-plugin-persistedstate` adapter. `lib/dataStorage.ts` exports `appStorage` (`getItem`/`setItem`), evaluated at call time: the file mirror when a desktop backend is initialised, `localStorage` otherwise. `plugins/00.data-storage.client.ts` (`enforce: 'pre'` and a `00.` prefix put it ahead of `plugins/pinia.ts`; no `dependsOn`, because `pinia.ts` also builds for the server where the client-only plugin does not exist) awaits `initDataStorage()` before Pinia is created, so no store hydrates empty because the load was pending. `plugins/pinia.ts` installs `createPersistedState({ storage: appStorage })`; the stores no longer name a storage.
- **Keys in the file:** `tasks-store`, `board-store`, `integration-health-store`, `taskStatistics`, `notionConfig`, `propertyOptions`, `settings-store` (#394, an additive key: the Fokus setting; an older build ignores it) (`PERSISTED_KEYS`). A Vitest guard instantiates every store and fails when a persisted key is missing. `kando-locale` (per-device, needed before Pinia) and `statistics-backfill-state` (idempotent job bookkeeping) stay in `localStorage`.
- **Envelope:** `{ schemaVersion, writtenAt, writtenBy, appVersion, stores: { "<key>": <parsed JSON> } }`. Stores are parsed objects (readable, diffable); the adapter stringifies at the plugin boundary. `writtenBy` is this device's id, which lives only in `data-location.json` (`{ folder, deviceId }`, app config dir, never in the synced folder).
- **Location and default.** The file is backed from the first start. Until the user picks a folder it lives in the app data dir (`~/Library/Application Support/com.julius.kan-do/`). The folder is remembered in `data-location.json`. A file in the default folder without a pointer is adopted, not re-initialised.
- **First run and import.** No `data-location.json` and no file: Rust answers `needsInit`, the webview builds the stores from `localStorage` (`utils/dataFile/importLocalStorage.ts`) and `data_init` creates the file. `localStorage` is left untouched. `data_init` is the only path that creates the file (first run, and "Hier neu beginnen" after `missing-file`) and refuses to overwrite one.
- **Safety states** (`Status` in Rust, `DataStatus` in TS): `ok`, `read-only-newer-schema`, `read-only-corrupt`, `missing-file`, `write-failed`. `ok` and `write-failed` may write; every other state blocks all writes and the app runs from memory with a persistent notice. `write-failed` retries on the next change and every 5 s while dirty and returns to `ok` after a successful write. A configured folder whose file is missing or unparsable is never re-initialised or overwritten. The same gate refuses to replace a file this process never read (`last_seen` is `None`), and a failed `data_init` out of `missing-file` leaves the state `missing-file` (it never lands in `write-failed`), so a returning volume is never overwritten from memory. An unreadable `data-location.json` pointing at the default folder is repaired by choosing that folder with `use` (move/replace to it stay refused). All of this is enforced at one choke point (`Shared::write_locked`, gated by `pre_write_check`).
- **Migrations** (`utils/dataFile/migrations.ts`) run on the raw envelope in the webview before hydration, from the file's `schemaVersion` to `CURRENT_SCHEMA_VERSION` (baseline 1, version 2 adds task sources, see [ADR 015](015-task-source-identity-and-persisted-shape.md); Rust's `SCHEMA_VERSION` must match, a Vitest guard compares them). A higher version hydrates read-only and is never down-migrated. A failing migration leaves the file alone and the stores empty (nothing is handed to Rust).
- **Changing the folder** (`data_set_location`): pending writes are flushed first and the switch is refused when that fails; the old file always stays. `move` copies into an empty folder (no reload), `use` switches to the data already there (window reload so the stores re-hydrate), `replace` overwrites the data there (explicit confirm in the modal). A newer-schema state is never copied down. A non-writable folder is refused.
- **Write ordering and the `use` switch.** `data_set` is an async Tauri command, so concurrent calls run on the async runtime in no guaranteed order. Every call therefore carries the `generation` of the last `data_load` and a per-page `seq` (`lib/dataBackendTauri.ts` stamps them synchronously at call time). Rust drops a `seq` that is not above the last applied one for the key (the newest store always wins) and any call whose `generation` is stale. `data_load` and a successful `use` switch bump the generation, and the backend does not adopt the one `data_set_location` returns, so between the switch and the reload's `data_load` the old webview cannot write its stores into the newly chosen file.
- **Unreadable pointer and unreachable backend.** An existing but unreadable `data-location.json` is not a first run: Rust enters `read-only-corrupt` (nothing imported, adopted or written) until the user picks a folder. If the `data_load` IPC itself fails, the webview runs read-only with the same notice instead of falling back to the frozen `localStorage` copy.
- **Single instance:** `tauri-plugin-single-instance`, registered first; a second launch focuses the running window.
- **Secrets never reach the file.** The writer itself strips `SECRET_STATE_PATHS` (ADR 007) from every store before the mirror and Rust see it (`utils/dataFile/stripSecrets.ts`, applied in `appStorage.setItem` and in the first-run import), so a Keychain bootstrap failure or a store that still carries a token in memory cannot put a token into the (possibly cloud-synced) file. The bootstrap keeps reading a legacy token from `localStorage`, which the import leaves untouched. Trade-off (accepted): the stripping is unconditional, not tied to #223's "Keychain verified" state. If the Keychain fails, a token the user re-enters is not persisted anywhere and after a restart the bootstrap restores the legacy copy from `localStorage`; on a non-macOS build tokens cannot persist at all. The start-up token apply is muted (#255 N1): the secrets bootstrap applies the Keychain tokens inside `withoutPersistence` (`lib/dataStorage.ts`), during which, and until the stores' pending `$subscribe` flush has run (`await nextTick()`), `appStorage.setItem` drops writes for the stores that carry a secret path. Without it an offline launch (unreadable data file, empty mirror) would send the Todoist-token apply to Rust as an edit and force a later recovery through the conflict choice. The window is start-up before mount, so no user edit falls inside it; it only removes a write path. The repo targets macOS, and a secret in a possibly cloud-synced file is the worse failure.
- **UI:** desktop-only `/settings/data` (web redirects to `/tasks`) plus a persistent single-line notice (`DataStorageNotice`, `role="status"`) above the board and on the page for every non-`ok` state; command palette entry and a link in the Notion settings header. See DESIGN.md.

## Hooks left for the sibling issues

- **#224 (backups, restore, conflicts)** filled them in, see [ADR 011](011-backups-and-conflict-safety.md): the hash check in front of every write, `before_replace`, the `beforeMigrate` backup and the rotating backup store.
- **#225 (updater):** the `data_flush` command and `useDataFolder().flushNow()` for the pre-update flush, then `useDataFolder().backupNow('pre-update')`; `appVersion` is already in the envelope.

## Consequences

- Each store change costs one IPC call with the whole store (tens to hundreds of KB). Acceptable at human edit speed; Rust coalesces the writes.
- The file is only as safe as its folder: a cloud-synced folder can produce conflict copies and a second device can change the file; #224 (ADR 011) detects both and keeps every version.
- On macOS the config dir and the default data dir are the same directory; the pointer file `data-location.json` stays there when the user picks another folder.
- A migration step must change at least one store value, because Rust only rewrites the file when a store differs.
- `cargo test` covers atomic writes, the safety states, the folder modes, debounce and max-wait coalescing; the real app (first-run import, Cmd+Q within 400 ms, kill -9, single instance) is verified by the manual checklist in the PR.
