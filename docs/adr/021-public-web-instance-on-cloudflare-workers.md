# ADR 021: The public web instance runs on Cloudflare Workers, behind a token gate

## Status

Accepted (epic #279; this ADR comes with its first slice #502; the proxy guards #503 are in it, the web CSP #504 is in it). The ADR number was taken as the next free one on `main` and may be renumbered at merge. Amended by #747 (2026-11-23): the Vercel deployment is shut down, the Worker is the only web host ("Consequences"). Amended by #742 (2026-11-23): the instance is local-only, see "Local-only"; the Notion proxy, its guards and its rate limiter are gone. Amended 2026-11-24 (Julius: "Previews: can they also be deployed on cloudflare as temporary deployments?"): design prototypes get gated Worker Previews, see "Prototype previews".

## Context

kan-do's web build ran on Vercel only. The homepage's secret launch (jaylouiz/jwue-homepage, milestone M2) needs the app reachable by invited people and by nobody else, on a free plan, next to the homepage's own Worker `www` on the same Cloudflare account. The app is a single-page app (`ssr: false`); only `/api/*` runs server code (the Notion proxy, the feedback relay, an unused Todoist token route). Nothing is stored server-side: user data lives in the browser's localStorage and in the user's own Notion or Todoist.

## Decision

- **Worker `kando` on `https://kando.julius-wuestefeld.workers.dev`** (Workers Free). The custom domain `kan-do.julius-wuestefeld.de` follows with the homepage's public launch (jwue-homepage M3) and is not part of this ADR. The gate cookie is `__Host-` bound, so the move needs no gate change.
- **Build: Nitro's `cloudflare_module` preset** (`npm run build:cloudflare`: `NITRO_PRESET=cloudflare_module`, and `NUXT_PUBLIC_FEEDBACK_RELAY_URL=/api/feedback` so the instance's feedback dialog posts to its own relay). `wrangler.jsonc` serves `.output/public` as Workers assets (static requests are free of charge) and runs the Nitro handler for `/api/*` and the SPA shell. `compatibility_flags: ["nodejs_compat"]` gives `Buffer` and `process.env` (vars and secrets). The desktop build (`npm run generate`, `src-tauri`) is unchanged (the Vercel build was too, until #747 removed it).
- **The gate is a Worker entry that wraps Nitro's built handler** (`worker/index.ts`, logic in `worker/gate.ts`, mirrors the homepage's gate), with `assets.run_worker_first: true` so static files pass it too. Rejected: a Nitro server middleware (Nitro's Cloudflare handler answers public asset URLs from the assets binding before any middleware, so `/_nuxt/*.js` would leak); Cloudflare Access (needs a zone and Zero Trust, and the user chose a shared token).
- **The token** is one shared secret, `GATE_SECRET` (the homepage's value, user decision 2026-11-18). A valid `?secret=` sets an HttpOnly, Secure, SameSite=Lax cookie `__Host-kd_gate` (the sha256 of the secret, 90 days) and redirects to the same URL without the parameter. Without it: 401 with a plain "Private preview" page (no app HTML, no script, no asset). `POST /api/feedback` and its `OPTIONS` preflight are exempt (desktop builds post without a cookie; the relay has its own hourly cap); `/api/notion/*` stays gated. While gated every response carries `X-Robots-Tag: noindex, nofollow` and `/robots.txt` disallows everything. `vars.GATE` is `"on"` in `wrangler.jsonc` (the single source: a fresh deploy is gated, and a dashboard toggle would be reset by the next deploy); `"off"` opens the app for the public launch (jwue-homepage #34), a deliberate change of that line through a PR; a missing `GATE_SECRET` with the gate on denies every request. A secret never appears in an issue, PR, commit or log.
- **Launch basics (#736, #738).** *Brand assets:* while the gate is on, a `GET` or `HEAD` of nine exact paths (`favicon.ico`, `favicon.svg`, `apple-touch-icon.png`, `icon-192.png`, `icon-512.png`, `icon-maskable-192.png`, `icon-maskable-512.png`, `og-image.png`, `manifest.webmanifest`; the table is `worker/public-assets.ts`) passes without the cookie, checked before the `secret` parameter like the feedback relay. No prefix, no case folding, no decoding; nothing of the app's code, shell or API is on it. The 401 page carries the `og:*` and `twitter:*` tags of the app shell, its image URL built from the request's origin (`worker/share.ts`), so a link-preview crawler (no cookie) shows name, tagline and image. Its status stays 401: whether every chat app reads tags from a 401 is unverified (check by pasting an invite link after a deploy; the fallback is answering that page with 200, still `noindex`). *Gate off:* the Worker builds `robots.txt` (allow all, `Disallow: /api/`, `Sitemap:`), `sitemap.xml` (the one canonical page `/`) and `/.well-known/security.txt` (RFC 9116: `Contact` is the repo's private vulnerability reporting URL, `Expires` 180 days after each request) from the request's origin (`worker/public-files.ts`). Rejected: static files in `public/` (one host baked in, an `Expires` that lapses silently, a copy on Vercel and in the desktop bundle). While the gate is on `robots.txt` stays disallow-all and the other two are gated. *Headers:* the same table gives the manifest `application/manifest+json` with `max-age=3600` and the icons and share image their type with `max-age=86400` (not fingerprinted); the Worker sets them on a successful non-HTML answer, and `routeRules` in `nuxt.config.ts` (built from the table) put them into the Vercel build's config (`vercel.json` `headers` are not part of the Build Output API config, measured with `VERCEL=1 nuxt build`). `_headers` would not reach Worker-served responses.
- **Local-only (#742, decision of Julius, 2026-11-23).** The public instance offers no Notion: Notion's developer terms (§ 3.1(l)) forbid a server that solicits or receives users' integration tokens, and the proxy did exactly that on every `/api/notion/*` request (legal research jaylouiz/jwue-homepage#94). It keeps all data in the browser's `localStorage`; the backup is the existing export/import on `/settings/data`. The desktop app keeps Notion unchanged: it calls `api.notion.com` itself and the token stays in the Keychain (ADR 007).
  - *Build:* `build:cloudflare` sets `__PUBLIC_CLOUD__` (`nuxt.config.ts`, read through `utils/publicCloud.ts`), and Nitro scans in no route that could receive a Notion token: `nitro.ignore` drops `server/api/notion/**`, `api/config/notion-key.ts`, `api/dev/**` and the stub-failure middleware for that preset. Dev, the E2E build and the desktop build keep them (the E2E Notion specs run against the local stub).
  - *Worker:* `/api/notion/*` (decoded, slash-collapsed, case-folded) answers 404 `NOT_AVAILABLE` behind the gate (`worker/guards.ts`), so no request reaches the app, which would otherwise answer an unknown path with the SPA shell.
  - *UI:* Notion shows disabled with "In der öffentlichen Cloud-Version nicht verfügbar" / "Not available in public cloud version" in the welcome flow and under "Eine App verbinden"; `/settings/notion` redirects to the sources tab. A Notion source stored in a browser from before (or imported) is paused, never rewritten: the board store leaves it out of `connectedIntegrations`, reads a Notion default as Local, nothing fetches or writes it (the adapter reports not configured before any request), and its Speicherorte row says "Nur in der Desktop-App verfügbar. Deine lokalen Aufgaben bleiben erhalten." and offers "Trennen" (removes the stored config and its cached tasks, no sync). The welcome flow skips its "Eine App verbinden" step there. The same data in a desktop build syncs again.
  - *Removed with it:* the origin check and the Durable Object rate limiter (`NotionLimiter`, a `deleted_classes` migration `v2` in `wrangler.jsonc`). They guarded only the Notion routes; the limiter's public fallback key (used when `GATE_SECRET` is unset, a finding of the research) is gone with it. Nothing else needed a limiter: the feedback relay keeps its own hourly cap.
- **The Notion proxy had three guards** (#503, #508; removed by #742, history below). While it ran, order gate → origin check → rate limit → app (`worker/pipeline.ts`):
  - *(removed by #742)* *Token out of the URL.* The browser sends the Notion token as `Authorization: Bearer` (`NotionClientAPI.getProxyOptions`); the server routes read only that header and ignore a `?token=` (`validateRequest`, `notion-stub-failure`), so no token ends up in Cloudflare logs or analytics.
  - *(removed by #742)* *Origin check* (`worker/guards.ts`): an `Origin` other than the Worker's own (`null` included), or `Sec-Fetch-Site` `cross-site` or `same-site`, answers 403 `FORBIDDEN_ORIGIN`, so no other website can use a visitor's browser as a Notion proxy. A request without `Origin` (curl, server to server) passes: this is no authentication (the token still is) and no defence against direct scripts. `/api/feedback` is open to every origin by design and not checked. The path is decoded, slash-collapsed and case-folded before matching, so `//api/notion/…` or `/api/%6Eotion/…` cannot skip the check.
  - *(removed by #742)* *Rate limit* (#503, reworked in #508): a Durable Object, `NOTION_LIMITER` (`worker/limiter.ts`, `durable_objects` in `wrangler.jsonc`), one object per client counting 120 requests per 60 s, so the count is exact across isolates and locations; over it answers 429 `RATE_LIMITED` with `Retry-After: 60` (the client sleeps a `Retry-After` of up to 10 s before its one retry and throws a longer one at once, #507, so a create under the limit stays pending for the next push) The client is `CF-Connecting-IP`, an IPv6 address by its /64 (`clientKey`). Measured: loading a Notion board is 5-6 requests, a status move 2 (`tests/e2e/notion-proxy-token.spec.ts`), so normal use stays an order of magnitude below. A missing binding, a failing object or an exhausted Durable Objects Free quota lets the request pass: the guard never blocks the app by itself, so under a flood the Worker's own Free request quota is the last bound. **Why not the Workers Rate Limiting binding** (what #503 shipped): live on workers.dev (Free) it never limited, 1200 requests in 28 s from one IP against 120 per 60 s all reached Notion, with no error in Workers Logs; the code was right (`wrangler dev` blocks the 121st request). Cloudflare documents the binding as approximate, counted per location from a local, eventually consistent count that "can exceed your configured limit", and others report the same non-enforcement on workers.dev (cloudflare/developer-platform#123, open, no reply); Cloudflare's own advice for a strict limit is a Durable Object. Cost: one Durable Object request per `/api/notion/*` request (Free: 100,000 a day, as many as the Worker's own requests); the class is SQLite-backed (`new_sqlite_classes`, the only kind Free allows) and checkpoints its window there (first hit of a window, then every tenth, rounded up, so a restored count is at most 9 above the true one), because an idle object is evicted after about ten seconds and a client could otherwise reset its window by pausing; nothing of a client outlives its window: the first write of a window sets an alarm at the window's end that deletes everything the object stored (`alarm()`), so no row stays per client ever seen; and the object's name is no IP: `idFromName` gets an HMAC-SHA-256 of the client key (`limiterName`), keyed with the existing `GATE_SECRET` (no new secret; without it, the gate off or a test, a public constant keys it, so the name is still no plain IP and the alarm bounds its life; keep `GATE_SECRET` set after the public launch). An IP is personal data and the Worker stores nothing of a visitor (epic #279); the alarm leaves, per client, at most one window of a count under a pseudonym, and Cloudflare's own request logs hold IPs regardless. Switching back is a `ratelimits` line and a `deleted_classes` migration. Rejected: keeping the binding as well (a second guard that does not fire is a false assurance), a Cloudflare zone rule (needs the custom domain; revisit at M3), an allow-list of Notion paths (the routes are fixed actions, no caller-chosen URL reaches Notion). Live check after a deploy: from one IP `seq 1 400 | xargs -P 20 curl … /api/notion/databases` (gate cookie, dummy bearer, no `Origin`) shows 120 × 401, then 429s with `Retry-After: 60`; a request after 60 s passes again.
  - *Dev surface:* `/api/dev/*` and `/api/notion/ping` answer 404 on the built Worker, `/api/config/notion-key` only reports `hasKey`, and `NOTION_KEY` stays unset. (Since #742 none of these routes is in the Cloudflare build: `/api/notion/*` is the Worker's 404, and `/api/dev/*` and `/api/config/notion-key` fall through to the SPA shell like any unknown path, with no server code behind them.)
  - *Server logs* (#511): Workers Logs persist the console, so a route logs a failure only through `logServerError` (`server/utils/serverLog.ts`): one line `[server-error] route=<path> status=<n> code=<c>`, the code an allow-listed pattern, never the error object, its message, a body, a header, a token or the query string (which holds database and page ids). The dev-only Notion response dumps are deleted rather than gated, so no `NODE_ENV` value can switch them on. `tests/server/api/notion/log-privacy.test.ts` fails when a route logs a task title or a token; a new `console.*` in `server/` needs the same proof. Three more paths close the rest (#525, #530): (1) *Nitro's own error log.* Nitro's default handler logs an unhandled throw as `[request error] [unhandled] [METHOD] <full URL>` plus the raw error; the production build registers `server/error-handler.ts` as `nitro.errorHandler` (set in the `nitro:config` hook, not as a config key: a key makes Nuxt skip its own handler and with it the `/__nuxt_error` page and the `vary` header), which wraps Nuxt's handler: it logs only through `logServerError`, hands Nuxt's handler a `defaultHandler` with its log off and sends the built-in JSON itself where Nuxt's handler leaves a JSON request unhandled or throws (not registered under `nuxt dev`); the task routes also answer 400 `INVALID_JSON` for a mapping that is valid JSON but no object (`parseMappings`), so that case is no unhandled throw at all. (2) *The Notion SDK's logger.* Every client comes from `createNotionClient` (`server/utils/notionClient.ts`: `logLevel` error and a no-op logger; the SDK logs only at debug, info and warn, its WARN `request fail` quotes the request); a test fails when `new Client(` appears in `server/` elsewhere. The factory also turns the SDK's own retries off (`retry: false`, #539): the SDK would retry a 429 twice, honouring `Retry-After` up to 60 s each, so the proxy would spend Notion quota inside the limit window and answer after the browser's 10 s timeout; the proxy throws the first error, `handleNotionError` forwards `Retry-After` and the browser client is the one retry policy. (3) *Workers Logs.* `wrangler.jsonc` keeps them on with `redact_query_string: true` and `logs.invocation_logs: false` (sampling 1): what persists is the allow-listed `[server-error]` line and nothing of a request (no URL, query, header or IP of ours). The Worker's own entry code (`worker/`) logs only through `logWorkerError` (`worker/log.ts`, #540): a constant message plus the error's name when it is a plain identifier, never the error object, message, stack or cause; `worker/log.test.ts` fails when another file there calls `console.`. The live instance gives up the per-request invocation lines (path, status, CPU time, outcome); Cloudflare's dashboard request and error metrics are unaffected. Switching back is one line in `wrangler.jsonc` and a deploy. Rejected: observability off (an outage would leave no trace), lower sampling (still persists URLs for the sampled share). Unverified: the exact field list of a Cloudflare invocation log; check in the dashboard after the first deploy that a request leaves no line and a thrown route leaves one `[server-error]`.
- **Content Security Policy** (#504; the desktop's is ADR 012, the same trade-offs): the Worker sets `Content-Security-Policy`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` on the app's `text/html` responses (`worker/csp.ts`, applied in `worker/pipeline.ts` behind gate and guards, so the gate's 401 page, its redirects and the guards' 403 and 429 are unchanged; JSON and assets get none). Policy: `default-src 'self'; script-src 'self' <hashes>; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self'; connect-src 'self' https://api.todoist.com; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'`. The feedback relay is same-origin on the instance (`/api/feedback`; the Notion proxy was too, until #742 removed it), so only Todoist (a webview-side `fetch`) is a second host. `script-src` carries the sha256 of the shell's two inline scripts (the import map and the `window.__NUXT__` config), which change with every build, and of the inline scripts the client injects at runtime through `useHead` (today one: Nuxt's built-in 404 page wires its "Go back" button; the shell cannot show it, so `csp-hashes.mjs` reads it from the built `_nuxt/*.js` chunks, #512): `nuxt.config.ts` prerenders `/200.html` for the Cloudflare preset (its build writes no HTML file; Nitro renders the same template per request), `scripts/csp-hashes.mjs` writes the hashes to `worker/csp-hashes.generated.json` (git-ignored; `build:cloudflare` runs it before the bundle check, which fails when the bundle lacks them), and `worker/index.ts` bundles them. `tests/config/web-csp.test.ts` fails when a built shell's inline script has no hash in the policy or the generated file holds a stale one, `worker/csp.test.ts` pins the directive list. Rejected: nonces (rewriting the HTML per request costs CPU on the free plan), a `_headers` file (no per-build hashes, skipped for Worker-served responses), hashing at request time. The web build has no feedback screenshot (native capture is desktop only, ADR 014), so `img-src` needs no `blob:` or `data:`; measured in Chromium against `wrangler dev`: the Local, Notion and Todoist boards, the feedback dialog with element pick, the settings pages, statistics and welcome raise no violation but the Todoist SDK's one `eval` probe (Todoist board only), an injected `<script>`, an inline event handler, a foreign `fetch` and a foreign image are blocked. **Vercel** served the app without a CSP (decision D2 of #504) until #747 shut that deployment down; the Worker is the only web host. Live checks after a deploy: curl shows the header on `/` and none on `/_nuxt/*.js` or `/api/*`; a browser session on the live URL has a clean console, an unknown path included (its 404 page still logs Nuxt's own `[NUXT_E1005]`, the `app:error` diagnostic of any 404, but no CSP violation).
- **No service worker.** The web build registers none, so a cached app shell cannot bypass the gate; a regression would show in `.output/public` (no `sw.js`) and in the code (`rg serviceWorker`).
- **No `NOTION_KEY`** on the instance, and the Notion stub stays off: `NODE_ENV` is inlined as production, `E2E_NOTION_STUB` and `NOTION_STUB_ENABLED` are never set as vars, and since #742 the build holds neither `/api/dev/*` nor any Notion route.
- **Pipeline: Workers Builds** (the homepage's setup): a push to `main` runs the build command `npm run build:cloudflare` and the deploy command `npx wrangler deploy` (`npm run deploy` is both in one for a manual deploy). The dashboard connection is a user step (Worker `kando` > Settings > Builds > Connect, a dashboard-created build token; the Worker, its secrets and the connection can equally be created through the Cloudflare API). Other branches: see "Prototype previews". There is no other web host: the Vercel deployment (`main`, `proto/*` previews and the `dev` instance) is shut down (#747). Its production deployment was the feedback relay target of the desktop builds until #281 switched them to the Worker; installed versions of before lost that relay.

- **Prototype previews** (2026-11-24). A pushed `proto/<n>-<slug>` branch (a design round's prototype, never merged) becomes a Cloudflare *Worker Preview* at `https://<name>-kando.julius-wuestefeld.workers.dev`, `<name>` the branch lowercased with every run of other characters turned into one `-` (`proto/725-onboarding-concept` → `proto-725-onboarding-concept-kando…`), cut with a hash suffix to 57 characters so `<name>-kando` stays one DNS label (`scripts/workers-preview.mjs`, `tests/config/workers-preview.test.ts`). So a prototype opens on any device while the Mac is off; the local `proto-serve.sh` link stays the fallback.
  - *Which branches:* Workers Builds runs the one build command for every branch. `build:cloudflare` (`workers-preview.mjs build`) builds only `main`, `proto/*` and anything outside Workers Builds (no `WORKERS_CI_BRANCH`); any other branch exits 0 at once. That saves the Nuxt build and the upload on 200+ PR branches a month, but not the clone and `npm ci` Workers Builds runs before the build command: each such push still takes the one build slot of Workers Free for a minute or two (a `main` deploy may wait behind it) and uses build minutes (3,000 a month). Should the dashboard's branch control get an include pattern, `proto/*` there removes that too. A branch cut before this change has no `preview:cloudflare` script: its build goes red once, harmlessly (merge `main` into it, or ignore it). The preview command `npm run preview:cloudflare` runs `wrangler preview --name <name> -c wrangler.jsonc` on `proto/*` only, refuses `main` and skips the rest.
  - *Worker Previews, not Version URLs:* a Version URL (`wrangler versions upload`) runs an uploaded version with the production vars and secrets, so a prototype uploaded that way would hold `FEEDBACK_GITHUB_TOKEN`. Prototypes therefore never go through `versions upload`. `preview_urls` is nevertheless `true`: wrangler maps it to the workers.dev subdomain's one `previews_enabled` switch, and without it a Worker Preview gets no URL ("no active URLs", wrangler 4.156). The side effect is a gated URL per production version (`<8 hex>-kando…`): production code and secrets on another host, the same gate, kept 30 days. A Worker Preview inherits no production var or secret: it gets `previews.vars` from `wrangler.jsonc` and the dashboard's Preview base config, and its own Durable Object namespace (the instance has none since #742). Previews need wrangler 4.135 or later (pinned: 4.156.2) and are an open beta.
  - *Safe by config:* `previews.vars` sets `GATE: "on"` (a missing var reads as on, too) and `FEEDBACK_RELAY: "dry-run"`: `POST /api/feedback` validates the report and answers `201 { ok: true, dryRun: true }` without any GitHub call, so a preview never files into the private feedback repository, also if a token were set. The Preview base config holds `GATE_SECRET` (the same token; without it a preview denies every request) and never `FEEDBACK_GITHUB_TOKEN`. Gate, CSP, the Notion 404, `X-Robots-Tag: noindex, nofollow` and the disallow-all `robots.txt` are the same code as production; Cloudflare adds its own `noindex` on preview `workers.dev` hosts. Data: a preview's `localStorage` belongs to its own host, so it shares nothing with the production instance, and the Worker stores nothing.
  - *The gate token:* the gate cookie is `__Host-` bound to one host, so each preview host needs the token once: open the preview link with `&secret=<token>` (or `?secret=` without a query); the gate sets the 90-day cookie and redirects to the same URL without it. Agents never write the token anywhere, so the links they post carry none.
  - *Cleanup:* `.claude/hooks/cleanup-merged.sh` deletes the preview (`workers-preview.mjs delete`, `wrangler preview delete`) together with the `origin/proto/*` branch, once the issue is closed. That needs `wrangler login` (or `CLOUDFLARE_API_TOKEN`) on the Mac; without it the branch still goes (the delete is not retried) and the preview stays: gated, files no feedback, and Workers Free keeps at most 100 previews per Worker, deleting the oldest. Unverified until the first preview build: that Cloudflare's preview host uses the `--name` as given, and that a fresh preview accepts the `v1`/`v2` migrations of the removed `NotionLimiter` (both show in the first build log).
- **The deployed Worker is `worker/index.ts`, never Nitro's own.** Under Workers Builds (`WORKERS_CI=1`) Nitro defaults `cloudflare.deployConfig` on, writes `.output/server/wrangler.json` and redirects `wrangler deploy` to it through `.wrangler/deploy/config.json`: the app and `/api/notion/*` would go live without the gate. `nuxt.config.ts` sets `cloudflare.deployConfig: false`, and `build:cloudflare` ends in `scripts/check-cloudflare-bundle.mjs` (a `wrangler deploy --dry-run` without `-c`, as the dashboard runs it; fails on a redirect or a bundle without the gate); `npm run deploy` also passes `-c wrangler.jsonc`. A local `wrangler dev` check misses this: `WORKERS_CI` is unset there (`WORKERS_CI=1 npm run build:cloudflare` reproduces the CI path).

## Limits checked (Workers Free)

Worker bundle 901 KiB, 210 KiB gzipped (limit 3 MB compressed); 217 static files (limit 20,000); static asset requests are not counted against the 100,000 requests per day; the routes mostly wait on Notion and GitHub (waiting is not CPU time, limit 10 ms). Over a limit requests fail; there is no overage bill.

## Consequences

- One host serves the web app: the Worker. The Vercel deployment is shut down (#747, Julius 2026-11-23, legal research jaylouiz/jwue-homepage#94: no CSP, no processor contract on the Hobby plan, an ungated copy of the app). `vercel.json`, the `vercel` preset fallback, the Vercel env checks of the Notion stub and of the dev instance, and `npm run deploy:dev` are gone; the project itself is deleted in the Vercel dashboard (Settings › Advanced › Delete Project), since removing the Git integration would leave old deployments reachable. Desktop builds post their feedback to the Worker since #281; installed versions from before that posted to Vercel and lose their relay with it (out of scope, Julius 2026-11-14, #281). Prototypes get a gated Worker Preview ("Prototype previews"), and the Look of a built change is checked on the Worker after the merge.
- Pitfalls of the build image: its npm must match the lockfile's npm (`packageManager` in `package.json` says `npm@11.19.0`, the version kan-do installs with), and `compatibility_date` must not be newer than the workerd of the pinned `wrangler` (`wrangler.jsonc` says which).
- Local checks: `.dev.vars` (git-ignored) holds a dummy `GATE_SECRET`, `npx wrangler dev --port <free port>` serves the built Worker.
